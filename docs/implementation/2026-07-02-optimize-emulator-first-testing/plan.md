# ① 计划 / 方案

## Plan Proposal

### 任务目标

把测试规范从「真机默认」改造成「**模拟器优先（emulator-first）+ 真机按需**」，并系统性压缩人工介入点：
1. 写入**设备阶梯路由策略**（L1 普通模拟器 → L2 root 模拟器 → L3 真机），每条用例可路由到最低可行层级。
2. 固化**锁屏/保活规范**（模拟器不锁屏 = 默认执行环境；真机安全锁屏 = 唯一化、批处理化的人工点）。
3. 固化**登录态快照**（模拟器 AVD snapshot 保存已登录态，验证码类人工降为一次性）。
4. 固化**模拟器结论可信度规则 + 网络噪声预检**（07-01 fake-IP 代理教训）。
5. 固化**外部依赖等待自动轮询规范**（07-01 证书轮询 9 次、多次问用户的教训）。
6. 写出**人工介入白名单**——白名单之外一律 AI 自主。

### 约束

- **docs-only**：不改 autotest 框架代码、不改 debox 代码、不动 `runs/` 历史记录。
- TEST_GUIDE.md 第五节规定「流程优化先提出 → 用户确认 → 改文档」：本任务由用户显式发起（指定了模拟器优先、双模拟器、锁屏差异三个方向），视为已授权方向；具体条文经 Codex plan review 把关，最终改动在任务归档时完整呈现给用户。
- 危险红线不放松：模拟器优先**不改变**「不清数据/不登出/不切环境/危险操作 pre-action 比对」等既有铁律；模拟器上的测试钱包为本地新建测试钱包（07-01 已有先例），真钱包规则不变。
- 不写 secret。

### 非目标

- 不做 CI 化、不做 B 模式（instrumented）用例扩充（那是按需求节奏走的事）。
- 不给真机做 root、不改真机锁屏安全设置（用户安全决策）。
- 不删除/降级真机测试的地位——真机仍是 L3 复核与最终验收的一环，只是不再是默认层。

### 建议方案（分 6 个改动点）

**P1 设备阶梯（emulator-first 路由）→ TEST_GUIDE 新章节 + TEST_CASES 模板列**

| 层级 | 设备 | 适用 | 判据 |
|---|---|---|---|
| **L1 普通模拟器** `Pixel_10_Pro_XL` | 默认层 | UI 流/导航/页面 render/功能黑盒/B 模式回归/弹窗/表单 | 不需要 root、不依赖真实网络路径与厂商特性 |
| **L2 root 模拟器** `debox_root` | 注入层 | 故障注入（DNS/iptables/hosts/回环）、双网切换（WiFi↔蜂窝）、需 root 的观测（`adb root`/系统文件） | 需要 root 能力或多网卡 |
| **L3 真机** 小米/三星 | 复核层 | ①模拟器网络噪声场景的 positively 复核 ②厂商特性/推送/性能/传感器 ③真实蜂窝/短信 ④最终验收抽核关键路径 | 结论受模拟器环境伪象威胁，或依赖真机独有硬件/网络 |

- 路由规则：每条用例取**能满足判据的最低层级**；`cases.md` 用例表加「设备」列（L1/L2/L3）。
- 降级规则：L3 真机不在线/锁死 → 该 case 标 `⏸️-待真机` 继续跑其余层级，**不整体阻塞**（07-02「真机掉线未测」的教训：当时整块搁置）。

**P2 锁屏/保活规范 → TEST_GUIDE Phase 1 扩充**

- 模拟器：开测执行 `adb shell svc power stayon true`；AVD 无锁屏（设置 None/Swipe），一次性配置进 devices.md 备忘。
- 真机：真机项**集中批跑**（一次解锁窗口内跑完）；开跑前人工解锁一次（安全锁 adb 不可绕过，列入人工白名单）+ `svc power stayon usb`；跑完恢复。
- Phase 1 检查清单加一行：「屏幕保活已设置（模拟器 stayon / 真机已解锁+stayon）」。

**P3 登录态快照 → USAGE 第 2/3 节 + devices.md**

- 模拟器完成登录（含验证码）后，关机打 AVD snapshot（命名如 `logged-in-testenv`）；后续轮次从 snapshot 冷启，验证码人工降为一次性。
- 快照恢复后必做健康基线：时间同步、网络可达、登录态有效（IM onOpen / 首页数据），不健康则重登（此时才需人工）。
- 真机不适用 snapshot，沿用「登录态易碎，只用不破坏」既有规范。

**P4 模拟器结论可信度 + 网络噪声预检 → TEST_GUIDE 新章节内小节**

- 开测预检（模拟器）：解析 1 个已知域名，判断是否落在 `198.18.0.0/15`（fake-IP 代理特征）；结果写 results.md 环境节。
- 结论分级：涉及 DNS 解析路径/连接目标/证书链的**网络层结论**，在命中噪声环境的模拟器上只能标【模拟器实测，待真机复核】；纯 App 内 UI/业务逻辑结论，模拟器即终局。
- 这是把 07-01「TC-N-05 结论务必真机复核」「BUG-002 模拟器伪象」教训固化成规则。

**P5 外部依赖自动轮询规范 → TEST_GUIDE 新章节内小节**

- 阻塞在外部（运维/后端/证书/DNS 下发）时：`/loop` 20min 间隔 ×6（≈2h）→ 未解除自动降频为每小时 → 累计约半个工作日仍未解除 → results.md 记录证据链并转 `⏸️-外部阻塞`，继续其余用例；**全程不逐次请示用户**，仅在转 ⏸️ 时汇报一次。
- 固化 07-01 证书轮询实践（当时 20min×6 + 每小时×3，但每次降频都问了用户）。

**P6 人工介入白名单 → TEST_GUIDE 新章节内小节 + USAGE 第 3 节 + CLAUDE.md 引用**

唯一合法人工环节（白名单，其余一律 AI 自主）：
1. 验证码/短信/2FA（且模拟器 snapshot 化后应趋近一次性）；
2. 真机首次解锁（安全锁屏，技术上不可绕过）；
3. 危险操作确认（`dangerous-ops.md` 命中且用例明确要求执行时的最终确认）；
4. 外部系统修复动作（运维/后端侧，不属于本测试可自动化范围）；
5. secret 注入（签名口令、API key 等，禁止 AI 索要明文进对话）。

白名单之外出现人工介入 → 视为流程缺陷，回写 lessons。

### 可选方案

- A（推荐）：如上，规范一次性成体系写入 TEST_GUIDE 新章节，其余文档只放速查/引用（单一权威源，防漂移）。
- B：只改 USAGE 教程加建议性文字，不动 TEST_GUIDE。——否决：USAGE 自身声明「规范正文见 TEST_GUIDE」，规则只写教程会造成两处权威。
- C：连同把真机项全部迁移模拟器（含最终验收）。——否决：07-01 已实证模拟器网络伪象会产生假结论，真机复核层必须保留。

### 推荐选择

A。

### 验证方式

- docs-only：验证 = ①各文档间引用/术语一致（设备名、层级命名、白名单条目不冲突）；②与既有铁律无矛盾（危险红线、登录态易碎、agent-dev-loop 修复流程不受影响）；③Codex 两轮 review（plan + impl）。
- 实测检验作为 follow-up：下一次 run 按新规范路由设备并统计人工介入次数（预期：常规轮次 0 人工）。

### 风险

1. **模拟器覆盖盲区**：厂商 ROM/推送/真实网络行为在模拟器测不到 → 由 L3 判据 + 最终验收抽核兜底（方案 C 的否决理由反向成为护栏）。
2. **图灵盾/反调对 root 模拟器策略变化**：当前实证不拦（lessons G3），若 SDK 升级开始拦 → Phase 1 健康基线会立刻暴露，届时降级回真机并回写 lessons。
3. **snapshot 状态漂移**（时间跳变/令牌过期）→ P3 已内置恢复后健康基线，失败才人工重登。
4. **TEST_GUIDE「稳定不变」定位**：本次为用户显式发起的规范演进，走本 agent-dev-loop 全程留痕，符合其自身的修订路径。
