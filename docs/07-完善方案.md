# DeBox AI 自动化测试 — 完善方案

> 版本：v1.0 | 创建日期：2026-06-05
> 路线：mobile-mcp 黑盒探索（广度/发现）→ 固化桥 → Espresso 白盒回归（深度/CI）
> 形态：里程碑 M0–M3，每个里程碑有明确 DoD（完成定义）

本文档基于对项目现状的深度盘点得出。结论一句话：

> **文档与框架都已成型（v1.5.1，约 4226 行源码 + 85 条单测），但"AI 驱动测 DeBox"这条核心链路从未真正跑通。** 投入最大的 Espresso 框架服务于"白盒回归"，而当前想要的"AI 驱动"属于"黑盒探索"，两条路线在代码层几乎不共享，连接它们的"固化桥"为 0。


**核心认知**：已写的框架服务于阶段③；mobile-mcp 服务于阶段①；**阶段②"固化桥"在代码层为 0**。
这条路线成败的关键不在补框架功能，而在**把①和③真正接起来**。

## 3. 关键技术决策（必须先拍板，否则后面返工）

### 决策① 登录/环境怎么处理？ —— 已定：用已登录账号 + 测试环境

**前提（已确认）**：测试目标 = **正式包 `com.tm.security.wallet`**（v2.12.2，已登录在用账号；设备另有独立测试包 `com.tm.security.wallet.test` v2.12.1，**本次不用**）。不需要测试账号，直接用已登录账号、在 DeBox 测试环境测，验证码问题**直接绕过**。

**DeBox 环境机制（已查证）**：
- 测试环境与正式环境是**同一个包**（`com.tm.security.wallet`），无独立测试包；靠 App 内 `SettingAdminActivity`（管理员设置页）开关切换，`BtcManager.isDebug()` 判断当前环境。
- **切换环境需重启 App 才生效**（`SettingAdminActivity` 原话："App必须重启，切换环境才会生效的，账号的正式数据也需要导入到测试环境"）。

**由此带来的硬约束（必须写进铁律，否则 AI 一个误操作就毁掉前提）**：

| 约束 | 原因 |
|---|---|
| ❌ **禁止 `clearAppData` / 卸载重装** | 会同时丢登录态 + 切回正式环境，又卡回验证码 |
| ❌ **禁止登出 / 切换环境操作** | 登录态与环境都是测试前提，不可在测试中破坏 |
| ✅ **"重置环境" = 仅 terminate → launch** | 重启不丢登录态、不丢测试环境设置，安全 |
| ✅ **每轮开跑前校验前提** | 启动后先确认"测试环境 + 已登录"（看昵称 / 进设置看环境标识），不符则停下报告，不要跑出一堆无效结果 |

**人工前置（一次性）**：测试开始前由你手动确认 App 已切到测试环境且已登录；AI 接手后全程**只用、不破坏**这个状态。
> ⚠️ 此约束需同步进 `docs/testing/TEST_GUIDE.md` 的操作铁律（当前铁律"每条用例重置环境 terminate→launch"成立，但要追加"禁止清数据/登出/切环境"）。

### 决策② 黑盒取不到元素（RN）怎么办？

DeBox 含 ReactNative 模块，mobile-mcp 靠 a11y 树取元素，RN/自绘控件常常拿不到 → 退化成坐标点击（脆、换分辨率就挂）。

**建议**：关键控件让 DeBox 给 RN 组件加 `accessibilityLabel` / 原生加 `contentDescription`。**这一改黑盒白盒双受益**（白盒 Espresso 也能用 `withContentDescription` 定位），是连接两条路线的隐性加分项。

**实测（2026-06-05，消息主页 `uiautomator dump`）**：70 节点 / 39 带 text / **60 带 resource-id**，class 全是原生 `TextView`/`ViewPager`/`RecyclerView`——**消息主页是原生 XML，不是 RN**，元素完全可取。黑盒可按 text/id 稳定定位（不退化坐标），白盒 `withId` 直接可用。`content-desc=0` 但 resource-id 充足可替代。
→ **结论修正**：RN 取元素担忧**仅对 DeBox 真正的 RN/H5 页面成立**（如部分活动/发现页），需到那些页面再验；主页及原生模块无需加 contentDescription。

### 决策③ 固化桥的形态？ —— 全方案的核心

| 方案 | 做法 | 评价 |
|---|---|---|
| A：维护 stepAction 映射表 | 一句中文 → 一段 Espresso 的查表 | ❌ 映射爆炸、极脆、伪自动 |
| **B：用例=规格，AI 直接写 Scenario**（推荐） | TEST_CASES.md 定位为"人读的规格"，AI 照规格用框架 DSL 手写白盒 Kotlin 用例 | ✅ 框架 DSL（`scenario{} / BaseScenario / flakyStep`）本就为此设计 |

**建议**：采纳 B，并**修正文档**——把"按用例自动执行"的表述降级为"用例是规格，AI 据此生成白盒代码"。AI 的价值在"看黑盒结果 → 写白盒代码"，不在"运行时解释 Markdown"。

### 决策④ DeBox 接入点选哪里？

13 模块大工程，不要污染主工程。**建议在 `app` 模块的 `src/androidTest` 接入 AAR**（已有 `AndroidJUnitRunner`），或新建一个只依赖 DeBox + autotest 的独立测试模块。

## 7. 风险

- **mobile-mcp 对钱包 + RN App 的兼容性未知** → M0-4 必须实测，别等到 M1 才发现取不到元素。
- **DeBox 是既有工程**，加 `contentDescription`、接入 AAR 需和 DeBox 团队协调 —— 这些是**外部依赖**，建议 M0 阶段并行去推。
- **登录态/测试环境是易碎前提**：靠人工一次性切好，AI 期间任何清数据/登出/切环境都会毁掉它 —— 已在决策①列为硬约束，需落实到铁律。
