## P3 背景：UI 自动化的两难
- 左：纯脚本（Espresso/Appium）——写得累、UI 一改就挂（维护成本）
- 右：纯 AI 测试（Midscene/Maestro AI）——灵活但慢、不确定、没法进 CI
- 讲稿钩子：要么累死人、要么进不了 CI，二选一？
- 来源：docs/10 §0

## P4 AutoTest 是什么：把两者焊接起来
- 一句话定位：**AI 在环探索发现问题 → 固化为确定性用例 → CI 自动回归** 的闭环测试体系
- 双相架构图：左框 AI 在环（Claude Code + mobile-mcp：看屏幕/规划/判定/读知识库，产出用例缓存+知识库）→ 产出 → 右框确定性执行（autotest AAR：零 LLM、缓存回放、自愈兜底）→ 报告回流
- 核心理念：Agentic authoring + Deterministic execution——所有 LLM 能力只定义接口、外部注入；CI 期不注入、自动降级为确定性行为并留痕
- 来源：docs/10 §0；docs/09 §0

## P7 优势①：为什么不在 App 里内置 AI
- 对比表：框架内调 AI API（已废弃：要 App 发 HTTP、AI 看不到屏幕、无法灵活交互）vs Claude Code + mobile-mcp（看截图、灵活对话、不改 App 代码）
- 来源：docs/10 §4.2

## P8 优势②：六大机制把 AI 与确定性焊接
- 表（机制 × AI 在环时 × CI 执行时）：三级自愈定位（注入 AI 兜底 / 不注入降级 L2）、固化桥缓存（READ_WRITE / READ_ONLY）、AI 软断言（注入评估器 / SKIPPED 留痕）、统计重试（历史通过率预算）、双链拦截器（全程证据）、根因签名（AI 读结构化根因 / 自动回填）
- 关键原则：LLM 只在 authoring 在环；execution 不注入、自动降级并留痕
- 来源：docs/10 §4.3

## P12 实际怎么用②：A+B 结合节奏（每个新需求）

## P14 测试规范①：八条铁律 + 危险红线
- 铁律：①AI 全程自主 ②按用例执行（cases.md 唯一来源）③/loop 5m 监工 ④最小人工介入（白名单五项）⑤修复走 agent-dev-loop ⑥先读知识库 ⑦危险操作 pre-action 比对 ⑧模拟器优先

## P15 测试规范②：监工 6-Phase 闭环
- 图：Phase1 确认环境 → Phase2 全量测试(P0→P1→P2) → Phase3 先写文档 → Phase4 修复（agent-dev-loop）→ Phase5 全量回归（仍 FAIL 回 P3 / 全 PASS 进 P6）→ Phase6 全量验收（不改码跑一遍）

## P16 测试规范③：设备阶梯（emulator-first）
- L1 普通模拟器（默认：UI 流/导航/回归）→ L2 root 模拟器（注入：DNS/iptables 故障注入）→ L3 真机（复核：厂商特性/真实蜂窝/验收抽核）；取最低可行层级，真机不在线不阻塞
- 讲稿：真机锁屏是历史上最大人工介入源；模拟器可无人值守
- 来源：USAGE §0.2；CLAUDE.md 铁律#8

## P17 原理深挖①：三级降级定位 + 指纹自愈
- 问题：UI 文案/布局微调 → 选择器失效 = 最大维护成本
- 降级链：L1 确定性（SelectorSpec sealed AST，DNF 展开驱动 BySelector，命中回写指纹）→ L2 指纹自愈（dump 层级→候选集→加权相似度：res-id 0.40/text 0.30/desc 0.20/class 0.10，空属性重归一化；相似度三档：相等 1.0/包含 0.8/归一化 Levenshtein×0.6；阈值 0.75 以下宁降级不硬认）→ L3 AI 兜底（可选注入）
- 防误愈：自愈/AI 命中只记 provisional 指纹（置信度封顶 0.85、24h TTL、不自动转正）；多命中无法消歧 fail-closed；自愈命中必生成 LocatorEvent 进报告要求人审（Healenium 教训）
- 来源：docs/10 §3.1；docs/09 §1

## P18 原理深挖②：固化桥（AI 探索 → 零 LLM 回放）
- 三层固化阶梯：AI 黑盒探索 → JSON 缓存确定性回放 → Kotlin 白盒用例（成本递减、稳定性递增）
- 关键设计：CachedStep.target 存完整元素快照而非裸选择器——回放时按 res-id→desc→text 稳定性排序重建选择器再走三级自愈 → 元素微调不破缓存
- CacheMode 三态：READ_WRITE（探索）/ READ_ONLY（CI，拒写留痕）/ WRITE_ONLY（强制重探索）；空用例/空缓存必 FAIL 防假绿；回放 CLICK 同样过危险守卫
- 来源：docs/10 §3.2；docs/09 §2

## P19 原理深挖③：双链拦截器（关注点分离）
- watcher 链（6 钩子）：纯旁路观察永不影响结果，自身异常 safely{} 吞掉但留痕——Logging / Screenshot（默认仅失败截图，scale 0.5+quality 80 省 ~75% 存储）/ Logcat（失败 dump 300 行）/ Performance（P50/P95）/ Memory（PSS 基线检泄漏）
- behavior 链：唯一允许影响结果的链——失败→按序尝试恢复→成功重试一次→全链无解抛错；DialogDismiss 只挂 behavior（默认词表不含「确认」类防误点危险确认）
- 踩坑沉淀：一次抓取所有 clickable 本地匹配，替代每步 23 次跨进程 findObject（被测 App 永不 idle 时的主耗时源）
- 来源：docs/10 §3.4；docs/01 §4

## P20 原理深挖④：统计化稳定性
- FlakyClassifier 规则链：自定义规则→内置关键词→内置正则→HARD_FAIL 保守兜底（宁可漏判 FLAKY 多跑一次，不把真 bug 误判成 FLAKY）
- AdaptiveRetryPolicy：由历史通过率 p 反解目标成功率 T 的尝试次数 **n = ⌈ln(1−T)/ln(1−p)⌉**（来自 1−(1−p)ⁿ ≥ T）；p=1→0 次不浪费、p=0→封顶；TestHistoryStore 每用例最近 50 次滚动窗口
- flakySafely 只重试 UI 时序类异常（AssertionError/ISE），刻意排除 NPE/RuntimeException——重试不能沦为掩盖 bug 的拖延器；只有 FLAKY 判定才吃预算，HARD_FAIL 直接失败
- 来源：docs/10 §3.3；docs/09 §4

## P21 原理深挖⑤：安全网关 + 约束即代码
- DangerousOpsGuard（v1.7，铁律#7 代码层）：全部点击入口（自愈定位/回放 CLICK/UiAutomatorExt）统一过闸——词表=内置+项目配置合并，命中 fail-closed 阻断+截图留证，显式 allowDangerous 才放行，事件回填报告
- 背后教训（L-002）：「AI 读文档自觉遵守」只覆盖 AI 在环路径；确定性执行路径（回放/自愈）必须代码级守卫——评审安全规则问「哪些执行路径绕过了纪律」
- 约束即代码另两例：TestSuite 只暴露 runAll() 不暴露 runFailed()（回归必须全量）；MonitorMode 独立线程+硬超时（App 卡死记合成 FAIL 不永久挂起）
- 来源：docs/09 §0；docs/10 §3.5；docs/lessons.md L-002

## P26 工程哲学：留痕不静默
- 表：自愈命中→LocatorEvent 进报告人审；AI 断言无评估器→SKIPPED 留痕；拦截器自身异常→safely{} 吞但留痕；缓存 READ_ONLY 拒写→留痕；根因分析失败→降级不影响失败记录；flaky 误判风险→保守 HARD_FAIL
- 一句话：没有任何静默兜底——所有非确定性行为、降级、异常，都 log/进报告
