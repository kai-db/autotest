## P3 解决了什么问题：UI 自动化的两难
- 左：纯脚本（Espresso/Appium）——写得累、UI 一改就挂，维护成本高
- 右：纯 AI 测试（Midscene/Maestro AI）——灵活但慢、不确定、没法进 CI
- 痛点钩子：要么累死人、要么进不了 CI，二选一？→ **本框架的解法：AI 在环探索发现问题 → 固化为确定性用例 → CI 自动回归**（下一页展开，案例章给实证）
- 来源：docs/10 §0

## P4 它是什么：把两者焊接起来（含系统全景）
- 一句话定位：**AI 在环探索发现问题 → 固化为确定性用例 → CI 自动回归** 的闭环测试体系
- 双相架构图：左框 AI 在环（Claude Code + mobile-mcp：看屏幕/规划/判定/读知识库，产出用例缓存+知识库）→ 产出 → 右框确定性执行（autotest AAR：零 LLM、缓存回放、自愈兜底）→ 报告回流
- 两条路线（原系统全景并入）：路线 A 自然语言→AI 规划→操控真机→截图理解→判定；路线 B git push→connectedAndroidTest→JSON/HTML 报告；闭环 = AI 发现 bug→固化用例→进 CI
- 核心理念：所有 LLM 能力只定义接口、外部注入；CI 期不注入、自动降级为确定性行为并留痕
- 来源：docs/10 §0；docs/09 §0；docs/01 §1 §2

## P10 怎么测试①：两种测试模式（先选对）

## P11 怎么实现 case②：两种模式各怎么建
- 左卡「模式 A · 建一次 run」：① 拷模板建 `runs/YYYY-MM-DD-功能名/`（`cases.md`+`results.md`）② 写 `cases.md`：项目信息表 + 用例表（编号/用例/步骤/验证标准/优先级 P0-P2）③ **先读 `app-knowledge/` 拿真实元素/弹窗/危险操作，别臆造 selector** ④ 标注前置条件、故障注入手段、危险红线（范例：`runs/2026-07-01-HTTPDNS回环bogon兜底/cases.md`）
- 右卡「模式 B · 写一条用例」：① 放 debox `androidTestAutotest/…/autotest/`，**继承 `DeBoxBaseTest`**（已封装启动+关弹窗+登录 preflight+selector 常量），不直接继承框架 `BaseUiTest` ② 用 `scenario("名"){ step(...){ } }.run()` DSL；定位优先 `byText/byResId/byDesc` + `locator.click(...)`（三级自愈）；断言用 `AppAssertions`，AI 软断言 `aiAsserter.assertWithAi(...)` ③ **只读+危险红线**：不点转账/签名/删除/登出/切环境，有副作用要复位 ④ 元素文案/id 用真机探测确认（范例 `DeBoxSmokeTest.kt`）
- 来源：USAGE §1（模式 A/B 建 case 步骤）

## P12 怎么实现 case③：A+B 结合节奏 & 谁留 A、谁沉淀成 B
- 一句话：A 是「每个新需求一次性的探索+发现」，B 是「累积的回归网」——**A 打头、B 沉淀、之后 B 兜底回归**，不是每次都两个全跑
- 流程图：新需求 → ①A 先行探索（建 `runs/日期-功能/cases.md`，AI 黑盒跑）→ ②发现 Bug → agent-dev-loop 修 → A 回归到全 PASS → ③**筛选沉淀 A→B**（挑「确定性+值得每次回归+纯 UI 能断言」的写成 B 用例）→ ④收尾（知识库回写+开关复位）
- A→B 筛选标准表（四判据）：确定性（时序/一次性→留 A；可稳定复现→B）｜判断类型（需人类级判断→A；纯 UI 状态断言→B）｜依赖（网络/DNS 注入/后端/验证码→A；App 内已登录 UI 流→B）｜回归价值（覆盖一次即可→A；每次改动都想复跑→B）
- 两条原则：① **A 发现的 bug，修复后补一条 B 回归用例**（fix-with-regression-test，A→B 最高价值沉淀点）② **B 是越攒越密的金字塔底座**，A 是每需求一次性的尖端探索——B 网越密、A 越省力
- 来源：USAGE §0.1

## P13 怎么实现 case④：端到端示例「资产页刷新」
- 五步走完 A+B 全链路（USAGE §6 原例）：
  1. **建 case（A）**：`runs/2026-07-10-资产页刷新/cases.md`，读 `app-knowledge/` 拿资产页元素，写 P0「进资产页→下拉刷新→数据更新且无 crash」（只读）
  2. **AI 驱动跑**：一句「按该 cases.md 跑测试」→ AI 读知识库→确认环境→逐条执行→危险比对→`results.md` 记结果（长测 `/loop 5m` 监工）
  3. **发现 FAIL**：AI 建 debox `docs/implementation/2026-07-10-fix-asset-refresh/` → plan → Codex review → 修 → Codex review → 回写 → 回归
  4. **沉淀回归用例（B）**：把稳定的「资产页加载」关键路径写成 `AssetPageSmokeTest : DeBoxBaseTest`，真机验通过纳入以后每次回归
  5. **收尾**：知识库补新元素；可泛化坑写 lessons；`autotest.enabled` 复位 false
- 讲稿：一个需求走完，A 发现问题、B 沉淀防复发——这就是日常节奏
- 来源：USAGE §6

## P14 怎么跑起来：两种模式的启动
- 模式 A：发一句「按 `runs/2026-07-XX-功能/cases.md` 跑测试」→ AI 自动 7 步：①先读知识库（元素/弹窗/危险操作/设备）②确认环境（按设备阶梯选设备→在线→屏幕保活→网络噪声预检→App 可启动）③按用例逐条执行（重置+截图验证）④危险操作 pre-action 比对 ⑤先记录再修复（写 `results.md`）⑥`/loop 5m` 监工 ⑦探索产物回写知识库
- 模式 B 五步命令：① debox `local.properties` 里 `autotest.enabled=true`（默认 off、CICD 不配 → **绝不进正式包**）② 选设备（模拟器优先，已登录+停在被测前置页）③ `./gradlew :app:connectedAppDebugAndroidTest`（或 `am instrument` 跑单条）④ 报告在 `/sdcard/Android/data/com.tm.security.wallet/files/autotest/report_*.json` ⑤ 测完 `autotest.enabled` 复位 false
- 来源：USAGE §2 §3

## P15 测试规范①：八条铁律 + 危险红线
- 铁律：①AI 全程自主 ②按 `cases.md` 用例执行（唯一来源）③`/loop 5m` 监工 ④最小人工介入（白名单五项）⑤修复走 agent-dev-loop ⑥先读知识库 ⑦危险操作 pre-action 比对 ⑧模拟器优先（设备阶梯 L1→L2→L3）
- 危险红线（钱包 App 不可逆·硬）：不清数据/不卸载/不登出/不切环境/不点转账·签名·删除；钱包·IM 只读浏览；**宁可用例 FAIL 也不误点**
- 不写 secret：token/私钥/助记词/密钥不进代码·日志·commit·断言（`local.properties` 存密钥，gitignored）
- 来源：CLAUDE.md 铁律；docs/10 §5；USAGE §5；TEST_GUIDE 二节

## P16 测试规范②：监工 6-Phase 闭环
- 图：Phase1 确认环境 → Phase2 全量测试(P0→P1→P2) → Phase3 先写文档 → Phase4 修复（走 agent-dev-loop）→ Phase5 全量回归（仍 FAIL 回 P3 / 全 PASS 进 P6）→ Phase6 全量验收（不改码跑一遍，全 PASS 结束 / 有 FAIL 回迭代修复）
- 三条关键规则：**每轮全量跑**（不能只跑 FAIL，「剩几条 ⏸️ 待执行」不算跑完）、**先记录再修复**（Phase3 早于 Phase4）、**验收是独立全新测试**（不复用旧结果，验收发现问题回迭代阶段不就地修）
- 来源：docs/10 §5.2；TEST_GUIDE 五节；CLAUDE.md 测试流程

## P17 测试规范③：设备阶梯（emulator-first）+ 人工介入白名单
- 设备阶梯：L1 普通模拟器（默认：UI 流/导航/回归）→ L2 root 模拟器（注入：DNS/iptables/回环故障注入、网络切换）→ L3 真机（复核：厂商特性/真实蜂窝/最终验收抽核）；取**最低可行层级**，真机不在线不阻塞（标 `⏸️-待真机`，其余照跑）
- 为什么模拟器优先：不锁屏、不被日常使用抢占、可 root 注入、可无人值守；**真机安全锁屏需人工解锁，是历史上最大人工介入源**
- **人工介入白名单（唯一合法五项，白名单外人工 = 流程缺陷回写 lessons）**：① 验证码/短信/2FA（snapshot 化后趋近一次性）② 真机首次解锁 ③ 危险操作确认 ④ 外部系统（运维/后端）修复 ⑤ secret 注入
- 来源：USAGE §0.2；TEST_GUIDE §7.1 §7.6；CLAUDE.md 铁律#8

## P18 测试规范④：bug 修复原则 + 修复走 agent-dev-loop（强制）
- **为什么不直接改代码**：直接改 = 无独立 review、无 plan 基线、无 VERDICT 把关，易引入回归、漏验证根因
- bug 修复四原则：① 证据驱动（根因基于日志验证，不凭猜）② 不引入新 bug（改前评估影响面，改后回归验证）③ UI/交互正常 ④ 最小改动（只改必须改的，不顺手重构）
- agent-dev-loop 闭环（每个 FAIL 一遍）：建 `docs/implementation/YYYY-MM-DD-动词-对象/` 任务目录 → 写 plan → **Codex 只读 plan review**（`VERDICT: PASS` 才落 Accepted Plan 基线）→ 按基线实现 → **Codex 只读 impl review**（无 Critical、无遗留 Important 才收尾）→ 回写 `results.md`
- 硬规则：VERDICT 驱动状态机；findings 只报 confidence≥80 的 Critical/Important；循环上限（plan 3 轮/impl 5 轮/consult 3 轮）超限升级用户；Codex 全程**只读**
- 来源：TEST_GUIDE 三节 + 六节；CLAUDE.md 铁律#5

## P19 原理精华：四个机制 + 两条招牌公式（原理 2 页合 1）
> Round 4 合并：删去原「六大机制 glossary 表」（与 P7 优势②焊接表重复），只留最有代表性的四机制 + 两条招牌公式；安全网关并入本页第 4 卡。

- 卡② 固化桥：AI 探索 → JSON 缓存回放 → Kotlin 白盒；缓存存**元素快照**而非裸选择器 → 元素微调不破缓存
- 卡③ 统计化重试：由历史通过率反解重试次数 **n = ⌈ln(1−T)/ln(1−p)⌉**（p=历史通过率；p=1→0 次、p=0→封顶）；只重试 UI 时序类异常，不掩盖真 bug
- 卡④ 安全网关 + 约束即代码：DangerousOpsGuard 全部点击入口统一过闸，命中 fail-closed 阻断+留证（L-002：确定性执行路径必须代码级守卫，与危险红线呼应）；`TestSuite` 只暴露 `runAll()`、`MonitorMode` 硬超时
- 讲稿：双链拦截器 / AI 软断言 / 根因签名等其余机制在 P7 焊接表已列，此处不重复；细节（DNF 展开、指纹 TTL、拦截器 6 钩子、滚动窗口）留答疑
- 来源：docs/10 §3 §3.5；docs/09 §0 §1 §2 §3 §4；docs/lessons.md L-002
