## L-002 安全不变量不能只写进流程纪律，必须下沉为框架代码守卫

- **背景**：2026-07-02 框架架构审计（`docs/implementation/2026-07-02-audit-framework-architecture/`），
  Codex plan-review R1 以 Critical 92 指出：铁律#7「点击前比对危险操作清单」只存在于 AI 黑盒流程的
  纪律层（TEST_GUIDE/CLAUDE.md 文字约束），框架代码的**全部点击入口**（SelfHealingLocator.click /
  UiAutomatorExt.clickText / UiReplayExecutor CLICK / EspressoExt.click）无任何守卫——B 模式回放、
  指纹自愈（还可能命中错误元素）点到「确认转账/删除钱包」时无人拦截。我方三路审查都只盯了
  DialogDismissInterceptor 一处，漏掉了系统性缺口。
- **教训**：对不可逆操作的防线，「AI 读文档自觉遵守」只覆盖 AI 在环的路径；**确定性执行路径
  （回放/自愈/封装点击）必须有代码级守卫**（统一点击网关 + fail-stop + 留证 + 显式 opt-in 放行）。
  评审安全类规则时，问法应是「**哪些执行路径绕过了这条纪律**」，而不是「哪个组件违反了这条纪律」。
- **固化位置**：修复 = 第一批任务 P0-0（DangerousOpsGuard 点击网关）。
- **日期**：2026-07-02

## L-003 审计提案项必须「要么实施、要么显式记延后」，杜绝无人认领的静默缺口

- **背景**：2026-07-02 框架审计产出 P0×10 / P1 六主题 / P2×10 提案，随后 5 任务实施到 v1.8.0。
  2026-07-03 新一轮审视（`docs/implementation/2026-07-02-optimize-framework-integrate-debox/`）发现
  C3、E1/E2/E3/E6、Q2/Q3/Q4/Q8 一组提案项**既未实施、也无任一任务记录延后原因**——不是评估后
  决定不做，而是任务拆分时漏接、无人认领，直到再审才暴露。
- **教训**：多任务承接一份审计清单时，每个提案项**终态必须二选一**：已实施（有 commit/测试）或
  显式延后（写明理由+触发条件，进 Follow-up）。二者皆无 = 静默缺口。收尾核对要拿**原始提案全集
  逐项对账**（本次用 Explore agent 对照 Accepted Plan 逐项判「实施/延后/未提及」），不能凭"大概都做了"。
- **固化位置**：v1.8.1 修 C3/E/Q4，Q2/Q3/Q8 补正式延后记录。
- **日期**：2026-07-03

## L-004 [candidate] 测「代码已修的证据」≠测「门禁已闭合」——模拟器/线上观测不替代真机硬门禁，如实标注闭合态

- **背景**：2026-07-10 回归 debox dev 07ae7655..HEAD 三提交（`2026-07-10-01`）。debox 侧挂账一条「Realm 恢复真机注入验证=2.14.3 放量硬门禁」。初版计划想用「autotest 在 L2 模拟器测试钱包做注入验证」去**闭合**它，被 Codex plan-review 连续三轮盯出：① 模拟器≠真机，模拟器证据是「恢复逻辑正确」的**必要非充分**证据，不能闭合真机门禁；② 一度把「Crashlytics 线上归零」写成真机门禁的替代完成条件，与自己定的边界自相矛盾。
- **教训**：测试产出要**分层标注证据强度与门禁闭合态**，绝不虚假宣称闭合（L4 家族）。① 模拟器/单测/代码核验 = 证「路径正确」；② 真机放量门禁只由真机清单闭合；③ 线上归零只由出包后 Crashlytics 观测闭合——三者不互相替代。真机全锁屏+真资产+装旧包时，autotest 能贡献的就是模拟器层增量证据，**如实写「模拟器已验证恢复逻辑，真机硬门禁仍未闭合」**，把未闭合项完整登记 Accepted Risk（owner/reason/follow-up/expiry 四要素齐）。
- **配套**：安全域测试注入设施走同 UID instrumented harness（`am instrument`），**禁 adb 广播钩子**（无认证、外部可触发篡改钱包 key，plan-review C-95）；模拟器上的破坏性注入用 **AVD 整盘快照**做事务式兜底（磁盘级原子，胜过逐文件 rename 的混合快照风险）。
- **固化位置**：`2026-07-10-01` Accepted Plan v4（AR-1~AR-6）；注入 harness = debox `2026-07-10-06`。
- **日期**：2026-07-10

## L-005 [candidate] 「入口不可达」必须探索到证据才可记 BLOCKED，未探索只能记 NOT_RUN——二者不可混用

- **背景**：2026-07-16 测 debox feat/share-refactor 分享弹窗 V2（`2026-07-16-01`）。11 类型中 SPACE/SPACE_FINISH/EVENT/DAPP 初版因「需重流程/时间不足」直接记 BLOCKED，被 Codex impl-review R2 判 Important：BLOCKED 需附「已尝试入口清单+截图」，仅「时间不足未探索」应记 NOT_RUN；且计划要求 P0→P2 全量执行，不能以文档标记替代实际执行。补测后：SPACE/SPACE_FINISH 建语音房实测**PASS**（原以为不可达其实可达）、EVENT（活动 Tab 空态截图）/DAPP（详情弹层无分享入口截图）实探后才是真 BLOCKED，5→7 类型 PASS，R3 转 PASS_WITH_ACCEPTED_RISK。
- **教训**：测试执行任务里 **BLOCKED = 已实际探索且证明入口不可达（附空态/无入口截图或主动规避理由）**；**NOT_RUN = 未实际探索**（要标 owner+复测条件）。别把「预判为难做」当 BLOCKED 直接跳过——很多「以为要重流程」的入口实测可达（如建语音房 3 步即得 SPACE 卡片）。评审会拿「有没有探索证据」卡这条，先做再下结论。
- **固化位置**：`2026-07-16-01` results.md（BLOCKED 均附截图路径）+ review.md Retro。
- **日期**：2026-07-16

## L-006 [candidate] 判 FAIL 必须先分类「产品 / 埋点 / 判据」——假阳性会驱动去改没坏的代码

- **背景**：2026-07-18 复查 07-17 记录的 BUG-001「冷启动出现 3 个 IM connect episode，只有最后一个 connected」，
  原判 P0 FAIL 并已登记修复。重新复现抓原始日志后证实是**假阳性**：JIM SDK 守卫全程正常
  （`same token is connecting` / `connection already exist`），`WS-Connect onOpen` **仅 1 次**、
  `onClose` **0 次**——自始至终只有一条 WebSocket。真实缺陷在埋点层（`ImConnectionEpisodeTracker.current()`
  永远返回最新 episode，导致 connected 回调被贴到 `-4` 上，真实建连耗时 1548ms 无人认领），
  而用例判据「connected 的 episode_id 与 connect_start 相同」测的是「调了几次 connect」而非「建了几条连接」，判据本身也错。
- **教训**：流程对**修复**有三重把关（plan review / impl review / VERDICT），对**判据**却零把关，
  而假阳性的代价高于漏测——它会一路走完 plan → Codex review → 改代码，
  Codex 审的是「改动是否符合 plan」，**不会质疑判据对不对**，最终改坏一个健康的钱包连接逻辑。
  故 FAIL 后必须先归类 A 产品 / B 埋点 / C 判据，且**分类必须基于独立于被质疑信号的证据**：
  怀疑「连接被重复创建」就去数底层 socket 事件与状态机迁移，而不是数应用层埋点条数。
- **固化位置**：`TEST_GUIDE.md` §5.3（三分类表 + `Defect Class` 字段，C 类禁改产品代码）。
- **日期**：2026-07-18

## L-007 [candidate] 证据要留「原始日志线路」而非结论摘要，否则分析无法异步、结论无法复核

- **背景**：同上复盘。07-17/07-18 两轮的 FAIL 证据均为 8 行散文结论（如
  `12-l2-wallet-switch-login-storm.txt`），零原始日志。次日复查时**必须重新复现**才能分析；
  而重现后拿到的决定性证据——SDK 守卫日志、`onOpen`/`onClose` 计数、状态机迁移序列、
  三次 connect 的 **tid==pid（主线程顺序重入，非多线程竞态）**——**一条都不在原记录里**。
  当初正是在证据不足下下了错误结论。
- **教训**：摘要会丢掉当时看不出重要性、事后才成为关键的字段（线程号、计数、状态机迁移）。
  必须落**过滤后的原始 logcat 整行**（保留时间戳/线程号/tag），而非人工提炼的结论。
  这与「分析记录限时 10 分钟」不冲突——**抓日志是机械且有界的，写结论才是无界的**，限时限的是后者。
- **固化位置**：`TEST_GUIDE.md` §5.4（evidence 目录结构 + 过滤而非摘要 + 保留计数类证据）。
- **日期**：2026-07-18

## L-008 [candidate] 流程要求的轮数必须与单位时间产能匹配，否则「卡死」是算术必然而非纪律问题

- **背景**：2026-07-18 复盘测试流程本身。原流程要求 Phase 2/5/6 **每轮全量、不复用结果**，
  最少三个完整轮次。实际产能：07-18 一轮推进 **6/22** 条、07-17 推进 **10/32** 条，
  且两轮的 results.md 都停在中途（07-18 写着「尚未进入 Phase 3」，07-17 任务目录 Status 停在 `planning` 一步未动）。
- **教训**：把「测着测着停了」归因为 AI 纪律问题、靠加规则约束，是**错误归因**——
  一轮都跑不完却要求三轮以上，中途终止是数学必然。正确解法按优先级是
  ①**降低单条成本**（确定性用例移出 MCP 走 AAR/cache 回放）②**并行**（多设备分片，原流程串行浪费数倍吞吐）
  ③**分层**（仅迭代期回归分层，验收全量不可让渡）。
  另注意：**验收门的 flaky 容忍必须严格**，否则 `0.98^30 ≈ 55%` 的全过概率会让验收永不收敛，
  但放宽标准又会变成掩盖真缺陷的后门——故 flaky 判定要求 3 次重跑全 PASS + 无 crash 签名 +
  可归因已知噪声 + 近 3 轮未重复，且 **P0 一律不得按 flaky 消化**。
- **固化位置**：`TEST_GUIDE.md` §5.6（并行分片）/ §5.7（分层回归）/ §5.8（flaky 严格门）/ §5.10（AAR 分层）。
- **日期**：2026-07-18
