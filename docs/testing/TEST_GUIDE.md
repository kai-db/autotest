## 一、测试前检查

```
1. 按设备阶梯选设备（见第七节；默认模拟器，真机仅 L3 场景）
2. 确认设备在线（adb devices 或 MCP list_devices）
3. 屏幕保活（模拟器 svc power stayon true / 真机人工解锁一次 + stayon usb）
4. 查看当前状态
5. 启动目标 App
```

## 二、操作铁律

- **模拟器优先**：设备按 L1 普通模拟器 → L2 root 模拟器 → L3 真机阶梯路由，取最低可行层级（详见第七节）；人工介入仅限白名单环节（§7.6）
- **操作前先获取元素**找坐标，不要盲猜
- **遇到弹窗先处理弹窗**
- **每条用例重置环境**（terminate → launch）
- **回归不能只跑失败的**：Phase 2 / Phase 6 必须全量；Phase 5 可按 §5.7 分层（必跑 P0 + 受影响面 + 历史 FAIL 过的），延后项须显式标记并在 Phase 6 补齐
- **用例集由影响面决定，不由改动行数决定**：写用例前必须做改动影响面分析（第八节），覆盖改动本身**与分析判定「行为会变」的既有功能**（`调用可达 ≠ 会受影响`，命中行为屏障即停止传播，见 §8.3）
- **先读知识库再探索**：每次 AI 测试 session 开始前先读 `app-knowledge/`（页面元素表、已知弹窗、跳转关系），避免重复探索；探索到的新元素/新弹窗回写知识库
- **登录态与测试环境是易碎前提，只用不破坏**：
  - ❌ 禁止 `clearAppData` / `pm clear` / 卸载重装（丢登录态 + 切回正式环境）
  - ❌ 禁止登出 / 切换环境操作
  - ✅ "重置环境" 仅指 terminate → launch
  - ✅ 每轮开跑前校验"测试环境 + 已登录"，不符则停下报告，不跑无效结果

### 危险操作 pre-action 比对（钱包 App 专项，借鉴 Mobile-Agent GUI-Critic）

**每次点击前**，若目标元素文本/语义命中 `app-knowledge/dangerous-ops.md` 清单
（转账确认、删除钱包、登出、清数据、切环境、授权签名等），**必须停下**：

1. 不点击，截图记录现场
2. 比对当前用例步骤是否明确要求该操作
3. 用例未明确要求 → 跳过并在 results.md 记录"遇到危险操作已规避"
4. 用例明确要求 → 仅在测试环境且金额/对象为测试数据时执行

钱包 App 误操作不可逆，宁可用例 FAIL 也不误点。

## 三、Bug 修复原则

每个 bug 修复方案提交前，必须确认：

| # | 原则 | 要求 |
|---|------|------|
| 1 | **证据驱动** | 根因基于日志验证，不凭猜测 |
| 2 | **不引入新 bug** | 改动前评估影响范围，修复后回归验证 |
| 3 | **UI/交互正常** | 确认无显示异常 |
| 4 | **最小改动** | 只改必须改的，不顺手重构 |

### 检查清单模板

```
- [ ] 根因基于证据验证
- [ ] 评估影响范围，无回归
- [ ] 确认 UI 正常
- [ ] 改动范围最小
```

## 四、测试执行流程

每条用例按以下步骤执行：

1. **重置环境** → terminate_app → launch_app → 等待启动
2. **执行操作** → 按用例步骤操作
3. **验证** → 检查页面状态
4. **判定** → PASS 或 FAIL + 抓取证据
5. **记录** → 写入本次 `runs/日期-功能/results.md`

## 五、自动化闭环流程（Claude Code 全权执行）

> 启动口令：「跑一轮完整测试」

> ⚠️ **强制规则（mandatory）**：本节流程不可跳过、不可简化、不可合并步骤。必须严格按
> Phase 1→2→3→4→5→6 顺序执行，每个 Phase 的子步骤都要完整跑完。任何"为了效率"省略环节
> 的行为都是违规。**Phase 结构与顺序属于「不可自主变更」项**——有优化建议先提出 →
> 获得用户确认 → 改本文档，再执行，不得自行省略。
> （与第九节「自我进化」的边界：**收紧/增量可自主，放松/削减需批准**，
> 而 Phase 结构、铁律、白名单、危险红线**即使是收紧也只能提议不能自改**，详见 §9.1。）
>
> **修复必须走 `agent-dev-loop` skill**：Phase 4 分析问题、修复代码**不直接改**，而是用
> Claude 计划/实现/修复/记录 + Codex 只读独立 review 的协作闭环（详见「六、修复阶段走
> agent-dev-loop」）。

### 前提条件

| 前提 | 说明 |
|------|------|
| 设备已连接 | adb devices 或 MCP 可见设备 |
| App 已安装 | 被测 App 已安装且可用 |
| 用户已授权 | Claude Code 拥有测试和修复权限 |

### 开始测试时

1. 在 `runs/` 下新建文件夹，命名为 `YYYY-MM-DD-功能描述`
2. **先做改动影响面分析，再写用例**（**第八节，强制**）——用例集必须覆盖改动本身
   **和分析判定「行为会变」的既有功能**，不能只测「改了什么」；但也不按调用可达性铺开（§8.3）
3. 基于 `TEST_CASES.md` 模板创建 `cases.md`，填入本次测试用例
4. 基于 `TEST_RESULTS.md` 模板创建 `results.md`（初始为空）
5. 执行闭环流程

> **AI 自动创建**：当用户提供测试用例（文字、文件、或口头描述）时，AI 应自动完成上述步骤——创建 `runs/日期-功能/` 目录，将用例整理到 `cases.md`，创建空 `results.md`，然后开始测试。
> **但用户给的用例是起点不是终点**——仍须按第八节做影响面分析并补齐受影响功能的用例。

### 闭环流程

```
══════════════════════════════════════════════════════════
  迭代修复阶段（循环，直到 0 个 FAIL）
══════════════════════════════════════════════════════════

  Phase 0: 未闭合任务扫描（§5.5）
  扫 docs/implementation/ 全部非终态任务（Status≠FIXED/CLOSED、
  VERDICT 空）→ 列清单写入本轮 results.md 开头
  → 本轮 FAIL 若命中已有任务目录，续跑而非新建
      │
      ▼
  Phase 1: 确认环境
  按设备阶梯选设备（第七节）→ 设备在线（无设备则启动模拟器）
  → 屏幕保活 → 模拟器网络噪声预检（§7.3）→ App 可启动
  → 分配并行设备与用例分片（§5.6）
      │
      ▼
  Phase 2: 全量测试（只测不修，FAIL 不阻塞）

    └── FAIL → ①抓原始日志线路（§5.4，机械动作，必做）
                ②三分类判缺陷归属（§5.3）
                ③agent-dev-loop「分析记录模式」建/续任务目录
                **不 plan、不改代码** → 立刻下一条
  ⛔ 严禁在 Phase 2 内修代码、跑 plan review、停下等人
      │
      ▼
  Phase 3: 更新文档
  将本轮全部结果写入 results.md（先记录再修复）
  汇总 FAIL 清单 + 各自任务目录链接
  统计行由表格生成并自校验（§5.9），不手写
      │
      ▼
  Phase 4: 全部修复（走 agent-dev-loop skill，见第六节）
  逐个 FAIL 续跑其任务目录：plan → Codex plan review →
  实现 → Codex 实现 review → 回写 results.md
  修完全部 FAIL 才进 Phase 5（不修一个跑一次）
      │
      ▼
  Phase 5: 分层回归（§5.7）
  必跑：全部 P0 + 本轮改动受影响面 + 历史 FAIL 过的全部用例
  可延后：与改动无关的 P2（标 ⏸️-分层延后，Phase 6 补齐）
  规则同 Phase 2：遇 FAIL 只分析记录，跑完再统一修
      │
      ├── 仍有 FAIL → 回到 Phase 3
      └── 全部 PASS → 进入最终验收
              │
══════════════════════════════════════════════════════════

              ▼
  Phase 6: 全量验收
  不改代码，完整跑一遍（含 Phase 5 延后的 P2）
      │
      ├── 全部 PASS → ✅ 测试通过，流程结束
      └── 有 FAIL → flaky 判定门（§5.8）

```

### 关键规则

- **测 / 修严格分离**：测试阶段（Phase 2 / 5 / 6）**只测不修**。任何 FAIL 都不打断遍历——记录完立刻下一条，跑完全部用例才进修复阶段
- **Phase 2 与 Phase 6 必须全量**；只有 **Phase 5 允许分层**（§5.7）。分层的每一条延后都要显式标 `⏸️-分层延后`，**"剩几条 ⏸️ 待执行"不算跑完**，要么跑完要么写明阻塞原因
- **绝不因为"跑不完"而缩减 Phase 6**——验收全量是最后一道防线。跑不完的正确应对是降低单条成本（§5.10 AAR 分层）和并行（§5.6），不是减少覆盖
- **FAIL 必须先过三分类（§5.3）再进修复**，防止假阳性驱动对健康代码的改动
- 必须**先更新文档（Phase 3）再修复代码（Phase 4）**
- **Phase 4 修复必须走 `agent-dev-loop` skill**（建 `docs/implementation/` 任务目录 + Codex review 闭环），不直接改代码——见第六节
- 最终验收是**独立的全新测试**，不复用之前结果；**验收阶段发现问题回到迭代修复阶段，不在验收阶段内就地修**

### agent-dev-loop 的两种调用模式

同一个任务目录跨阶段续跑，测试期只写前半段：

| 模式 | 用在 | 动作 | 产出 |
|---|---|---|---|
| **分析记录模式** | Phase 2 / 5 / 6 遇 FAIL | 建 `docs/implementation/YYYY-MM-DD-NN-fix-xxx/`，`index.md` 写 Status=`ANALYZED`、复现步骤、截图/logcat 证据、初判根因 | 只有 `index.md`，**无代码改动** |
| **修复模式** | Phase 4 | 续跑同一目录：plan → Codex plan review → 实现 → Codex 实现 review → Status=`FIXED` | plan/implementation/review + 代码改动 |

分析记录模式**单条限时 10 分钟**：证据抓够就收，根因判不准就写「待 Phase 4 深挖」，不在测试期做深度调查。

### 防卡死铁则（不许停下等人）

测试期间 AI 拥有最高权限自主推进。以下情况**一律不问用户、按预案自动处理**：

| 卡点 | 自动动作 |
|---|---|
| 单条用例 > 15 分钟无进展 | 判 `FAIL-超时`，抓截图+logcat，进分析记录模式，下一条 |
| App 崩溃 / 白屏 / 无响应 | terminate → launch 重试 1 次；仍失败 → 判 FAIL，下一条 |
| 元素找不到、定位失败 | 重取元素树 1 次 → 仍无 → 判 FAIL 记录「元素缺失」，下一条 |
| 设备离线 / adb 无响应 | `adb kill-server && adb start-server`，重连 1 次；模拟器则重启 AVD |
| 命中危险操作清单 | 按 §二 规避，记「已规避」，**不问用户**，下一条 |
| 依赖外部系统 | 转 `⏸️-外部阻塞`（§7.5 轮询），继续其余用例 |
| Codex review 循环超上限 | 按第六节升级，该 case 转 `⏸️-需人工`，继续其余用例 |
| 真机不在线 | 该 case 标 `⏸️-待真机`，继续（§7.1 降级规则） |

**唯一允许停下的情形**：§7.6 人工介入白名单五项。其余任何"要不要继续 / 要不要这样修"都由 AI 自行决断并在 results.md 记录决策依据。

**⛔ 反模式**（出现即违规，回写 lessons）：
- 跑到第 3 条 FAIL 就开始改代码 → 剩余用例永远没跑
- 一条用例反复重试 5 次以上不判定
- 在测试中途向用户提问后静默等待

### 5.3 FAIL 三分类（判 FAIL 后、建任务目录前必做）

> **来源**：2026-07-18 复盘。BUG-001「冷启动多 IM episode」被判 P0 FAIL 并登记修复，
> 深挖原始日志后证实是**假阳性**——JIM SDK 守卫正常工作（`same token is connecting`
> / `connection already exist`），全程 `onOpen` 仅 1 次、`onClose` 0 次，**只建了一条连接**。
> 真实缺陷在埋点层（episode 归属错），判据本身也测错了对象。
> 若按原流程直接进修复，会驱动去改一个没坏的钱包连接逻辑。

流程对**修复**有三重把关（plan review / impl review / VERDICT），对**判据**原本零把关。
假阳性代价高于漏测——它会驱动对健康代码的改动。因此每个 FAIL 必须先归类：

| 类别 | 判断方法 | 去向 | 禁止 |
|---|---|---|---|
| **A 产品缺陷** | 用户可感知的行为错误，且有独立于埋点的证据（UI 状态、持久化数据、真实网络行为） | 进 Phase 4 修产品代码 | — |
| **B 埋点/可观测性缺陷** | 产品行为正确，但日志/指标记录错误（错配、漏记、口径错） | 进 Phase 4，**只改埋点层** | ⛔ 不得改产品逻辑 |
| **C 判据缺陷** | 产品和埋点都对，是用例的机器判据写错了对象 | **改 `cases.md` 判据**，原 FAIL 改判 | ⛔ 不得改任何产品代码 |

**分类必须基于独立证据,不能只看被质疑的那个信号。** 典型手法：怀疑「连接被重复创建」，
就去数**底层 socket 事件**（`onOpen`/`onClose`）与**状态机迁移**，而不是数应用层埋点条数。

分类结论写进任务目录 `index.md` 的 `Defect Class: A|B|C` 字段。**C 类不建 implementation 任务**，
直接在 results.md 记「判据修正」并改 cases.md。

### 5.4 证据规范：必须留原始日志线路

> **来源**：2026-07-18 复盘。07-17/07-18 两轮的证据是 8 行散文结论、零原始日志，
> 导致次日复查时**必须重新复现**才能分析；而重现后拿到的决定性证据
> （SDK 守卫日志、`onOpen` 计数、状态机迁移）**一条都不在原记录里**——
> 当初的结论正是在证据不足下下错的。

判 FAIL 时**必须落盘原始日志线路**，不是结论摘要：

```
runs/日期-功能/evidence/phaseN/
├── NN-<case>-raw-lane.log     # 过滤后的原始 logcat（保留时间戳/线程号/tag）
├── NN-<case>-launch.txt       # am start -W 输出（LaunchState/TotalTime）
└── NN-<case>-<现象>.png       # 关键节点截图
```

- **过滤而非摘要**：用 `grep -E "<相关tag>"` 保留整行原文，**保留时间戳与线程号**
  （tid==pid 可判主线程重入 vs 多线程竞态，摘要会丢掉这个信息）
- **保留计数类证据**：建连/断连/重试等次数，写明是数的哪个信号
- 敏感信息按各 run 的红线脱敏（token/密钥/完整地址），但**不得因脱敏而丢弃结构**
- 这条与「10 分钟限时」不冲突：**抓日志是机械且有界的，写结论才是无界的**——限时限的是后者

### 5.5 Phase 0：未闭合任务扫描

> **来源**：2026-07-18 复盘。`2026-07-17-01-...` 任务目录 Status 停在 `planning`、
> VERDICT 空、checklist 全未勾，BUG-001 从记录之日起**一步未动**。
> 流程定义了状态，却没有任何环节去扫描"谁卡在中间态"。

每轮开测前（Phase 1 之前）执行，零成本止血：

```bash
# 列出所有非终态任务
grep -L "Final VERDICT: \(PASS\|FAIL\|PASS_WITH_ACCEPTED_RISK\)" docs/implementation/*/index.md
```

- 结果写入本轮 results.md 开头的「未闭合任务」节，每条注明 **owner + 卡住原因 + 本轮是否处理**
- 本轮 FAIL 若命中已有任务目录（同一现象/同一根因），**续跑该目录并追加 Round N，不新建**
- 非终态任务**超过 2 轮未推进**必须升级给用户，不允许无限挂账

### 5.6 并行执行（设备分片）

设备清单见 `app-knowledge/devices.md`。**同层级多设备时按用例分片并行**，不串行：

- 分片键取**用例互不干扰**为准：不同账号/不同钱包/纯只读用例可并行；
  共享同一测试账号且会改状态的用例**必须串到同一设备**，避免互相污染
- L2 注入类用例（iptables/DNS）**独占设备**，不与其他用例并行
- 每片独立记录设备 ID 与证据目录，results.md 汇总时标注来源设备
- 并行不改变判定标准；某片卡住按防卡死铁则处理，**不阻塞其他片**

### 5.7 Phase 5 分层回归

> 全量回归的成本模型：07-18 一轮实际推进 6/22、07-17 推进 10/32，
> 而流程要求最少三个完整轮次。**要求跑不完的轮数，等于要求流程中途终止。**

Phase 5（迭代阶段的回归）按下表分层，**Phase 2 与 Phase 6 不适用分层**：

| 必跑（不可延后） | 可延后到 Phase 6 |
|---|---|
| 全部 P0 | 与本轮改动无关的 P2 |
| 本轮改动的受影响面（按 Phase 4 各任务的影响范围评估取并集） | |
| **历史曾 FAIL 过的全部用例**（防回归主力） | |

- 延后项标 `⏸️-分层延后` 并写明依据，**Phase 6 必须补齐**
- 受影响面判断存疑时**默认纳入必跑**，宁可多跑
- 分层是**为了让循环能收敛**，不是为了少测——Phase 6 全量是不可让渡的底线

### 5.8 Phase 6 flaky 判定门（严格标准）

> 单条 flake 率 2% 时，30 条全过的概率仅 `0.98^30 ≈ 55%`——
> 接近一半概率因偶发抖动被打回全量重跑，验收可能永不收敛。

Phase 6 出现 FAIL 时先过 flaky 判定，**判定标准必须严格，否则会变成掩盖真缺陷的后门**：

判为 flaky 需**同时**满足：

1. 定向重跑 **3 次全部 PASS**（同设备、同环境、不改任何代码）
2. 失败现场**无** FATAL / ANR / OOM（`diagnosis/LogcatAnalyzer` 无 crash 签名）
3. 失败原因可归因到**已知环境噪声**（§7.3 模拟器 fake-IP、设备卡顿、外部依赖抖动），
   且该噪声有独立证据，不是"没查出原因所以算 flaky"
4. **该用例近 3 轮内没有因同一现象被判过 flaky**——同一条反复 flaky 视为真缺陷

任一条不满足 → **按稳定复现处理，回到迭代修复阶段**。

- 所有 flaky 判定必须记入 results.md「Flaky 登记」节：用例 / 重跑记录 / 归因证据 / 累计次数
- ⛔ 禁止用 flaky 判定消化 **P0 用例**的 FAIL；P0 一律按真缺陷处理
- 判定为 flaky 的用例进 Follow-up，由框架 `stability/FlakyClassifierApi` 沉淀历史

### 5.9 results.md 统计自校验

> **来源**：2026-07-18 复盘。该轮统计行写 `PASS 2 / FAIL 1 / BLOCKED 3 / NOT_RUN 16`，
> 按其自身表格逐行数实为 `PASS 6 / FAIL 1 / BLOCKED 4 / NOT_RUN 11`。
> 两者合计都是 22，所以**看着没毛病**，实则统计行与表格互相矛盾。
> 该统计是"该不该进 Phase 4"的决策输入，错了会连锁。

- 统计行**由表格生成，不手写**：

  ```bash
  awk -F'|' '/^\| *[0-9]+ *\|/{print $4}' results.md | sort | uniq -c
  ```
- 写完 results.md **必须跑一次核对**，统计行与表格不一致时以表格为准并修正
- 各状态计数之和必须等于用例总数（和对不上说明有行漏标状态）

### 5.10 回归提速：AAR 分层执行

回归轮次用 `com.autotest:autotest` AAR（instrumented）跑**能脚本化的确定性用例**，其余仍走 MCP：

| 走 AAR（B 模式） | 走 MCP（A 模式） |
|---|---|
| 有明确机器判据的（单飞/熔断/租约/落库/兼容矩阵） | UI 探索、跳转关系、弹窗形态 |
| 已沉淀 `docs/testing/cache/*.cache.json` 的可回放用例 | 需人类判断、跨系统、网络注入编排 |

- **AAR 不背全量回归**——只吃确定性子集。用例少时建测试 APK 的固定开销反而更慢，批量重跑才回本。
- 链路已就绪：`autotest/build.gradle` `LIB_VERSION` → mavenLocal → debox `app/build.gradle`
  `androidTestImplementation "com.autotest:autotest:<版本>"`，受 `local.properties` 的 `autotest.enabled` 控制（默认 off）。
- **每轮把 MCP 跑稳的用例回写成 cache json**，让 AAR 覆盖率逐轮滚大，MCP 只留探索面。

### 监工模式

测试期间使用 Claude Code 内置 `/loop 5m` 开启监工模式，每 5 分钟自动检查 AI 执行状态，防止卡住：

```
/loop 5m 检查测试进度：当前跑到第几条/共几条。若同一条用例 5 分钟无进展，
按「防卡死铁则」判定该条并推进下一条；若在测试阶段发现正在改代码，立即停止修复回到遍历
```

## 六、修复阶段走 agent-dev-loop（强制）

> Phase 4 的每个 FAIL，以及测试中发现的代码问题，都必须经此闭环修复，**不直接改代码**。
> **注意**：测试阶段（Phase 2/5/6）只用「分析记录模式」写 `index.md`，本节的完整闭环
> （plan → review → 实现 → review）**只在 Phase 4 跑**，见第五节「两种调用模式」。

### 为什么

直接改代码 = 无独立 review、无 plan 基线、无 VERDICT 把关，容易引入回归、漏验证根因。
agent-dev-loop 让 Codex 以**只读**身份独立评审 plan 与改动，形成"计划→评审→实现→评审"闭环。
（历次测试都没走这步——`docs/implementation/` 至今为空，这正是要纠正的偏离。）

### 步骤（每个待修问题一遍）

1. **建任务目录** `docs/implementation/YYYY-MM-DD-动词-对象/`，默认四件：
   `index.md`（权威入口：当前 Status + 最终 VERDICT）/ `plan.md` / `implementation.md` / `review.md`
2. **写 plan** → 调 Codex 做 plan review（只读）→ 修到 `VERDICT: PASS` 或
   `PASS_WITH_ACCEPTED_RISK` → 在 `plan.md` 写下 `Accepted Plan` 基线
3. **按基线实现**，进度/偏差记 `implementation.md`；真遇歧义/风险再 consult Codex
4. **自检后**调 Codex review 改动（对照 Accepted Plan）→ 修到无 Critical、无遗留 Important
5. **收尾**：`index.md` 写权威 Status / 最终 VERDICT / 小结；可复用经验回写
   `docs/lessons.md`（项目级）或全局 ledger
6. **回写 results.md**：该 FAIL 的修复结论 + 链接到对应 `docs/implementation/` 任务目录

### 硬规则

- `VERDICT`（`PASS` / `FAIL` / `PASS_WITH_ACCEPTED_RISK`）驱动状态机；findings 只报 confidence ≥ 80 的 `Critical` / `Important`
- 循环上限：plan review 3 轮、实现 review/fix 5 轮、consult 3 轮 → 超限升级给用户
- Codex **只读**（不传 `--write`）；不写密钥到代码/文档/日志；高风险操作先问用户

> 完整协议见 `agent-dev-loop` skill。被测 App（DeBox）代码在 `debox-android` 工作区；
> autotest 框架自身代码改动同样走本闭环。

## 七、设备策略（emulator-first）

> 目标：**尽量减少人工参与**。模拟器不锁屏、不被日常使用抢占、可 root 注入，
> 是默认执行环境；真机降为「复核层」，只在模拟器给不出权威结论时使用。
> 设备清单/能力矩阵见 `app-knowledge/devices.md`（开测前必读）。

### 7.1 设备阶梯与路由规则

| 层级 | 设备 | 定位 | 适用 | 判据 |
|---|---|---|---|---|
| **L1** | 普通模拟器（`Pixel_10_Pro_XL`） | 默认层 | UI 流/导航/页面 render/功能黑盒/弹窗/表单/B 模式回归 | 不需要 root，不依赖真实网络路径与厂商特性 |
| **L2** | root 模拟器（`debox_root`） | 注入层 | 故障注入（DNS/iptables/hosts/回环）、WiFi↔蜂窝切换、需 root 的观测 | 需要 root 能力或多网卡 |
| **L3** | 真机（小米/三星） | 复核层 | ①模拟器网络噪声场景的 positively 复核 ②厂商特性/推送/性能/传感器 ③真实蜂窝/短信 ④最终验收抽核关键路径 | 结论受模拟器环境伪象威胁，或依赖真机独有硬件/网络 |

- **路由规则**：每条用例取**能满足判据的最低层级**；`cases.md` 用例表标注「设备」列（L1/L2/L3）。
- **降级规则**：L3 真机不在线/锁死 → 该 case 标 `⏸️-待真机`，**继续跑其余层级用例，不整体阻塞**。
- 危险红线不因层级放松：模拟器同样执行危险操作 pre-action 比对；L2 注入后按 `devices.md` 复原清单复原。

### 7.2 锁屏与屏幕保活

- **模拟器**：无锁屏（AVD 一次性配置屏幕锁 = None）；每轮开测 `adb shell svc power stayon true`。
- **真机**：安全锁屏（指纹/Bouncer）adb 不可绕过——真机用例**集中批跑**，开跑前人工解锁一次（白名单环节 §7.6）+ `svc power stayon usb`，跑完恢复设置。
- Phase 1 检查项：「屏幕保活已设置（模拟器 stayon / 真机已解锁+stayon）」。

### 7.3 模拟器结论可信度 + 网络噪声预检

- **预检（模拟器开测必做）**：解析 1 个已知域名，若结果落在 `198.18.0.0/15`（宿主 fake-IP 代理特征）→ 本轮为噪声环境，写入 results.md 环境节。
- **结论分级**：
  - 涉及 DNS 解析路径/连接目标/证书链的**网络层结论**，在命中噪声环境的模拟器上只能标 **【模拟器实测，待真机复核】**，不得直接判 PASS/FAIL 定论（TC-N-05/BUG-002 教训：模拟器伪象险些误判客户端 bug）；
  - 纯 App 内 UI/业务逻辑结论，**模拟器即终局**，无需真机复跑。

### 7.4 登录态快照（模拟器专属）

- 模拟器完成登录（含验证码，人工一次）后打 AVD snapshot（`logged-in-<env>`）；后续轮次从快照恢复，验证码人工降为一次性。
- 快照恢复后**必做健康基线**：时间同步、网络可达、登录态有效（IM onOpen / 首页数据正常）；不健康才人工重登。
- 真机不适用 snapshot，沿用「登录态易碎，只用不破坏」规范（第二节）。

### 7.5 外部依赖等待自动轮询

阻塞在外部系统（运维/后端/证书/DNS 下发）时，不逐次请示用户：

```
/loop 20min 间隔轮询 ×6（≈2h）
  → 未解除：自动降频为每小时一次
  → 累计约半个工作日仍未解除：results.md 记录证据链，
    该 case 转 ⏸️-外部阻塞，继续其余用例，汇报用户一次
```

每次轮询结果（时间点 + 观测值）记入 results.md，形成证据链（07-01 证书轮询实践固化）。

### 7.6 人工介入白名单

**唯一合法**的人工环节（白名单之外一律 AI 自主；出现计划外人工介入 = 流程缺陷，回写 lessons）：

1. **验证码/短信/2FA**（模拟器 snapshot 化后应趋近一次性）；
2. **真机首次解锁**（安全锁屏，技术上不可绕过）；
3. **危险操作确认**（`dangerous-ops.md` 命中且用例明确要求执行时的最终确认）；
4. **外部系统修复动作**（运维/后端侧，不属于本测试可自动化范围）；
5. **secret 注入**（签名口令、API key 等，禁止 AI 索要明文进对话/日志/文档）。

### 7.7 被测包自主构建与安装（AI 自主，非白名单）

> **规范来源**：2026-07-11 实证。此前「用户 AS 打包」是无据的临时做法——打包/安装**不在** §7.6 白名单，按铁律必须 AI 自主。本节固化自主流程，**严格遵循，勿再退回人工打包**。

**debox `:app` debug 包 CLI 自主构建**（RN 0.78 手动集成 + CodePush 的坑，详见 debox `docs/lessons.md` L-BUILD-01）：

1. **补 `react` 扩展 shim**（构建前）：`app/build.gradle` 的 `apply from: codePushGradle` **之前**插入——
   ```gradle
   if (project.extensions.findByName("react") == null) {
       project.extensions.add("react", [debuggableVariants: project.objects.listProperty(String).convention(["appDebug"])])
   }
   ```
   （原因：手动集成未 apply RN 插件 → codepush 读不到 debuggableVariants → 误对 flavored `appDebug` 触发 JS bundle → 撞未注册任务。shim 让 debug 正确跳过 bundling，走 Metro。）
2. **构建**：`NODE_PATH="$PWD/ReactNative/node_modules" ./gradlew :app:assembleAppDebug`；需 Realm 注入 harness 时加 `:app:assembleAppDebugAndroidTest`（`local.properties` 先设 `autotest.enabled=true`）。
3. **构建后 `git checkout app/build.gradle` 还原 shim**（只为构建，不入库）。
4. **安装预检（I-89）**：`apksigner verify --print-certs` 比对新 APK 与已装包签名一致（debug 用 release keystore，通常同签名）+ 新 versionCode ≥ 已装 → `adb install -r`（保留登录/钱包数据）。**签名不符或降级 → 停止报告，绝不 uninstall/清数据**（触犯 §7.6 与危险红线）。
5. **归因链**：记录源码 HEAD SHA + APK sha256 + versionCode + 签名摘要 + 安装后 `dumpsys package`；版本号可能与线上重号，**用运行时行为探针证「改动确在包内」**（如 PicSel 面包屑 / RealmKey 恢复日志 / 缓存行为）。
6. **产物校验**：`adb ... am start` 冷启验证进 MainActivity、登录态在、logcat 无 FATAL —— 通过才算被测包就绪。

> CLI 只覆盖 debug；release/上架包仍走正式签名流程。模块级编译/单测（`:im:imKit`/`:business:*`）加 `NODE_PATH` 即可（L18）。

## 八、用例设计规范（影响面驱动，强制）

> **核心诉求**：改动不能影响其他功能、不能带出新 bug。
> 因此用例集的边界**不由改动的代码行决定，而由改动的影响面决定**。
> 「只测改了什么」是最常见的漏测来源——回归 bug 恰恰出在改动者没想到的下游。

### 8.1 用例设计也走 agent-dev-loop

写 cases 与修代码同级，**不是随手列几条**，走同一套闭环（T1/T2 按规模定）：

1. 建任务目录 `docs/implementation/YYYY-MM-DD-NN-design-cases-<功能>/`
2. `plan.md` 写：**改动清单 → 影响面分析 → 用例矩阵**（含覆盖依据）
3. **Codex plan review 的评审重点是「覆盖是否有洞」**——不是评审用例写得好不好看，
   而是问「哪些受影响功能没有对应用例」「哪些判据无法机器验证」「哪些边界没覆盖」
4. 修到 `VERDICT: PASS` 才落 `Accepted Plan`，据此生成 `runs/日期-功能/cases.md`
5. 测试过程中新发现的影响面，回写该任务目录并补用例（记 Round N）

### 8.2 影响面分析（写用例前必做）

按下列顺序推导，**每一层的产出都要写进 plan.md，不能只写结论**：

| # | 步骤 | 方法 | 产出 |
|---|---|---|---|
| 1 | 锁定改动集 | `git diff <base>..HEAD --stat`，逐文件列改动符号（类/函数/字段/配置） | 改动清单 |
| 2 | 反查上游调用方 | codegraph / Explore agent 查每个改动符号的**全部调用方**（含动态派发、回调、事件总线、反射） | 谁会因此变化 |
| 3 | 顺查下游依赖 | 改动符号**依赖的**组件与共享状态（单例、缓存、DB、SP、全局事件） | 谁的状态被它改 |
| 4 | 找共享资源竞争 | 与改动共用同一资源的**其他功能**（同一张表/同一缓存/同一连接/同一锁） | 易被殃及的邻居 |
| 5 | 列跨端/跨进程面 | RN bridge、IM 长连接、推送、深链、多设备互踢等**跨边界**影响 | 边界外的影响 |
| 6 | 汇总受影响功能清单 | 去重合并 2~5 的结果，**每条标注影响路径与判断依据** | 用例矩阵的输入 |

> **事件总线 / `observeForever` / 全局单例是影响面分析的重灾区**——它们让调用关系不出现在
> 静态调用链里。2026-07-18 的 IM 排查即为例：`SwitchWallet(SUCCESS)` 有三个同时存活的观察者
> （其中 `Application.kt` 用 `observeForever` 且从不移除），grep 改动文件完全看不出来。
> **务必显式检索事件名/常量名的全部订阅点**。

### 8.3 建 case 的判定标准（**判定为会受影响的才建，不按可达性铺开**）

> **范围收敛原则**：`调用可达 ≠ 会受影响`。按可达性铺 case 会爆炸且稀释重点。
> 唯一判据是——**该功能的可观测行为（输出 / 持久化状态 / 时序 / 错误路径）是否可能改变**。

**沿调用链传播时，命中「行为屏障」即停止，不再往下扩**：

| 行为屏障（到此为止，下游不再建 case） | 说明 |
|---|---|
| 改动对该层的**输入输出契约完全不变** | 内部实现调整，调用方看不见 |
| 中间层做了**归一化/兜底**，把变化吸收掉了 | 变化传不下去 |
| 下游只依赖**未被改动的字段/分支** | 与改动正交 |

**建 case 判定表**：

| 情形 | 处置 |
|---|---|
| 改动直接修改的功能 | **必建**，P0 |
| 分析确认**行为会变**的调用方 / 下游 | **必建**，P0/P1 |
| 共享资源（同表/同缓存/同连接/同锁）且**存在读写交叉**的功能 | **必建**，P1——回归高发区 |
| 可达但**分析确认行为不变**（命中上表任一屏障） | **不建**，plan.md 一行写明屏障依据 |
| 仅编译期依赖 / 与改动正交 | **不建**，无需逐条说明 |
| 分析后仍判不准 | **先花几分钟读代码定性**；定性后仍不确定才建 case（这类应是少数） |

- 目标是**每条 case 都能说清「因为 X 变了，所以 Y 可能坏」**；说不清因果的 case 就是噪声，不建。
- 豁免只需**一行依据**，不必长篇论证——重点是可被 review，不是堆文档。
- ⛔ 仍然禁止的是**凭直觉说「应该没影响」就跳过**；豁免必须指向具体屏障。

### 8.4 用例书写要求（尽量详细）

沿用 `TEST_CASES.md` 表格列，每条 case **六要素齐全**，缺任一项视为未完成：

| 要素 | 要求 |
|---|---|
| **用例 / 变更来源** | 关联到具体 commit / 改动符号,**写明它属于影响面的哪一层**（8.2 第几步推出的） |
| **前置与动作** | 精确到可复现：账号/钱包/网络状态/起始页面 + 逐步操作,不写「进入相关页面」这种模糊表述 |
| **机器判据** | **可机器验证**且**写明数的是哪个信号**（见下方红线）；含数量词（恰一次/≤1/无）而非「正常」 |
| **优先级 / 设备** | P0/P1/P2 + L1/L2/L3（按第七节取最低可行层级） |
| **复原与危险边界** | 用完怎么复原；命中 `dangerous-ops.md` 的操作写明边界 |
| **证据要求** | 该 case 需落哪些原始日志线路 / 截图（§5.4） |

**判据红线（L-006 教训）**：判据必须写明**观测哪个信号**，且该信号要能独立于被测实现。
反例:「connected 的 episode_id 与 connect_start 相同」——测的是应用层埋点调用次数，
而非真实建连数，导致假阳性。正例:「`WS onOpen` 恰 1 次且 `onClose` 0 次」——直接数底层事件。

### 8.5 用例集完整性自检（交付前）

- [ ] 影响面清单每一条都有对应 case 或**一行屏障依据**（§8.3）
- [ ] 每条 case 都能说清「因为 X 变了，所以 Y 可能坏」——说不清因果的已剔除
- [ ] 每条 case 六要素齐全，判据均可机器验证且写明观测信号
- [ ] 覆盖了**改动本身**与**受影响的既有功能**两类，不只有前者
- [ ] 事件总线/全局单例/共享缓存的订阅方与使用方已显式检索并覆盖
- [ ] 历史曾 FAIL 过的相关用例已纳入（§5.7 必跑项）
- [ ] 已过 Codex plan review 且 VERDICT 为 PASS / PASS_WITH_ACCEPTED_RISK

## 九、自我进化（AI 自主沉淀与优化）

> **目标**：测试过程中发现的不合理之处能自主修正，有价值的经验能自动沉淀，
> 让每轮测试都比上一轮更快、更准。
> **但进化必须有方向约束**——否则「自我优化」会退化成「自我放宽」，
> 悄悄削掉覆盖和安全红线，且因为是 AI 自己改的，没人会发现。

### 9.1 单向棘轮原则（不可违反）

**收紧可自主，放松需批准。** 判断依据是「这条改动让测试变严还是变松」：

| 方向 | 示例 | 权限 |
|---|---|---|
| **收紧 / 增量** | 新增 case、新增危险操作条目、判据变严、新增元素表条目、新增 lessons、补充卡点预案 | ✅ **AI 自主**，记录即可 |
| **等价重构** | 同等效力下让表述更清晰、合并重复条目、修正笔误与失效引用 | ✅ **AI 自主**，需在进化日志写明「等价性依据」 |
| **放松 / 削减** | 删 case、降优先级、判据变松、删危险操作条目、放宽 flaky 标准、缩小覆盖、跳过 Phase | ⛔ **必须用户批准**，禁止自主执行 |

**存疑时按「放松」处理**——即需要批准。

⛔ **绝对不可自主变更**（即使看起来是收紧）：铁律条目本身、Phase 结构与顺序、
§7.6 人工介入白名单、危险操作红线（钱包不可逆操作）。这些只能提议，不能自改。

### 9.2 可自主沉淀的四类产物

| 产物 | 位置 | 沉淀时机 |
|---|---|---|
| **App 知识** | `app-knowledge/screens/*.md`、`dangerous-ops.md` | 探索到新元素/新弹窗/新危险入口时**立即**回写 |
| **用例缓存** | `docs/testing/cache/*.cache.json` | 用例稳定跑通且判据可被缓存格式表达时 |
| **经验教训** | `docs/lessons.md`（项目级，标 `[candidate]`） | 每轮收尾 retro；跨项目通用的进全局 ledger |
| **稳定性历史** | `stability/TestHistoryStore` | 框架自动，无需人工 |

**沉淀质量要求**：写「**为什么**」而不只是「是什么」。
反例:「切钱包会触发多次登录」。正例:「切钱包触发多次登录，因为 `SwitchWallet(SUCCESS)`
有三个同时存活的观察者，其中 `Application.kt` 用 `observeForever` 且从不移除——
**事件总线订阅点不出现在静态调用链里，影响面分析必须显式检索事件名**」。
后者下次能直接复用，前者不能。

### 9.3 进化触发点

以下情形**必须**触发一次沉淀，不允许"跑过就算":

| 触发 | 动作 |
|---|---|
| 探索到知识库没有的元素/弹窗/跳转 | 回写 `app-knowledge/` |
| 发现新的危险操作入口 | **立即**补 `dangerous-ops.md`（收紧，自主） |
| 同一问题**第二次**遇到 | 写 lessons——第二次说明不是偶然 |
| 出现计划外人工介入（白名单外） | 记 lessons，标为流程缺陷（§7.6） |
| 用例判据被证明测错对象 | 改判据（收紧或等价→自主；放松→报批）+ 记 lessons |
| 某卡点防卡死铁则没覆盖到 | 补一条预案（收紧，自主） |
| 假阳性 / 假阴性 | **必记 lessons**，且复盘判据设计 |

### 9.4 进化日志（可追溯，不许静默改）

**所有自主进化都必须留痕**，写入本轮 `runs/日期-功能/results.md` 的「本轮进化」节：

```markdown
## 本轮进化

| # | 类型 | 改了什么 | 方向 | 依据 |
|---|---|---|---|---|
| 1 | 知识库 | ShareDialogV2 新增 3 个元素定位 | 增量 | 探索发现，截图 evidence/xx.png |
| 2 | 判据 | TC-C-001 改数 `WS onOpen` 而非 episode_id | 等价→收紧 | 原判据测错对象，见 L-006 |
| 3 | 提议 | 建议 TC-F-003 降为 P1 | **放松-待批准** | 需删钱包无法执行，已 BLOCKED 3 轮 |
```

- **方向列必须如实标注**；标错方向（把放松写成收紧）是严重违规
- 「放松-待批准」项**本轮不执行**，汇总报告用户，批准后才改
- 每轮收尾核对：进化日志条数 ≥ 触发点命中数（§9.3），否则说明有该沉淀而未沉淀

### 9.5 反模式

- ⛔ **为了让本轮变绿而改判据**——判据修改必须有独立于"想让它过"的技术依据
- ⛔ **把反复失败的用例默默降级或删除**——这是放松，必须报批
- ⛔ **沉淀成流水账**：只记现象不记因果，下次无法复用
- ⛔ **静默改规范**：改了 TEST_GUIDE / 铁律却不进进化日志
