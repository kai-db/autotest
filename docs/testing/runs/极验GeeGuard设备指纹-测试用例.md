# 极验 GeeGuard 设备指纹接入 — 测试用例文档

| 项 | 值 |
| --- | --- |
| 功能 | 极验 GeeGuard 设备指纹 SDK 接入（替换腾讯图灵盾 RCE） |
| SDK 版本 | com.geetest.core GeeGuard v2.7.1.1（AAR 内置，含 arm64-v8a / armeabi-v7a / x86 / x86_64 SO） |
| 首个携带版本 | 2.14.2（以实际发版为准；此前线上版本不携带 `gee_token`） |
| 文档日期 | 2026-07-13 |

## 一、背景说明（测试必读）

1. **这不是滑块验证码**。GeeGuard 是**无感设备指纹采集**，全程没有任何用户可见的验证 UI。测试关注点是：① 请求里是否正确携带 `gee_token`；② 各种异常下业务是否**不受阻**（客户端 fail-open 设计）；③ 后端风控命中时业务侧的失败表现。
2. 工作原理：App 启动后（首页展示后、子线程）初始化 SDK 并异步采集设备环境 → 缓存 token → 4 类风控业务场景发请求时，从缓存**同步非阻塞**取 token 塞进请求 body 的 `gee_token` 字段 → 后端拿 token 调极验服务判定风险，决定放行/拦截。
3. token 两种形态（后端均可解析，测试时用长度区分）：
   - **respondedGeeToken**：SDK 提交极验服务端成功（status=200）返回，**长度约 1K 字符**（正常主路径）；
   - **geeToken**：极验服务端不可达/出错时（-300/-500/-501）降级用本地生成 token，**长度约 4K 字符**。
4. 客户端兜底原则：token 采集失败/未就绪 → 请求**不带** `gee_token` 字段（不是带空串），由后端 fail-open 放行。任何情况下**不允许 crash、不允许阻塞业务请求**。

## 二、影响范围（涉及接口与入口）

| # | 后端接口 | 业务场景 | 客户端触发入口 | token 位置 |
| --- | --- | --- | --- | --- |
| 1 | `app_login` | 登录/注册 | 创建钱包、导入钱包、第三方导入后自动登录 | JSON body 字段 `gee_token` |
| 2 | `liveroom/join` | 加入语音房 | ① 普通用户点语音房卡片 → 加入弹窗（含密码房/付费房）；② 房主点自己的进行中语音房直接进房 | form body 字段 `gee_token` |
| 3 | `lucky_box/receive_lucky_box` | 群聊普通红包领取 | 群聊中点开红包 → 点"开" | form 参数 `gee_token` |
| 4 | `lucky_box/onchain_box/receive` | 链上宝箱红包领取 | 群聊/语音房中点开链上宝箱 → 点"开" | form 参数 `gee_token` |
| 5 | `liveroom/lucky_box/rob` | 语音房红包领取 | 语音房内点开红包 → 点"开" | form 参数 `gee_token` |

不涉及：其他所有接口（全局 header 注入已移除，仅上述 5 个接口的 body 携带）；短信/邮箱验证码等场景未接入。

## 三、测试环境准备

1. **包**：debug 或测试渠道包，且打包机已配置 `GEEGUARD_APP_ID`（local.properties / CI 注入）。⚠️ 拿到包先跑 TC-A1 确认 AppID 已配置，否则整轮测试都在测降级路径。
2. **抓包**：Charles/mitmproxy 可看请求 body 中 `gee_token` 字段及其长度（~1K vs ~4K）。若正式包有证书校验，改用日志方式验证（见附录）。
3. **日志**：logcat 过滤 tag `GeeGuard`。约定：日志只打 token 长度和状态码，**绝不打印 token 内容**（本身也是一条用例 TC-I3）。
4. **设备矩阵**：
   - 真机 arm64（主流机型，Android 10~15 各一台）
   - 真机 armeabi-v7a（32 位老机型，如有）
   - 模拟器 arm64 镜像（Apple Silicon Mac 上的 AVD）
   - 模拟器 x86_64 镜像（Intel 机器 AVD）⚠️ 重点：APK 的 abiFilters 只打包 arm64-v8a + armeabi-v7a，x86_64 模拟器上 SO 加载会失败，走兜底路径，这是专门的用例（TC-F3）
5. **老版本包**：线上最新已发布版本 APK 一份（用于新老版本兼容与覆盖升级）。
6. **后端配合**：能查风控调用日志（确认收到 token 且解析成功）；能对指定测试账号/设备下发"高风险拦截"策略（验证拦截表现）；能确认 fail-open 配置。
7. **极验后台/运维配合**：设备指纹白名单（风险码 60113）添加/移除能力。

## 五、附录：验证方法

**1. 抓包看 gee_token**
- Charles 抓 HTTPS，关注上表 5 个接口；`app_login` / `liveroom/join` 看 JSON/form body，红包 3 个接口看 form 参数。
- 长度判断形态：~1000 字符 = 正常（respondedGeeToken）；~4000 字符 = 降级（本地 geeToken）；无该字段 = 未就绪/采集失败（合法，走 fail-open）。

**2. 日志验证（抓不了包时）**
- `adb logcat | grep GeeGuard`，关键行：
  - `submitReceipt ok, respondedGeeToken.length=xxxx` → 采集成功
  - `submitReceipt failed status=-300/-500/-501, degrade to geeToken.length=xxxx` → 降级成功
  - `GEEGUARD_APP_ID not configured, skip register` → 包没配置 AppID（先找开发）
  - `GeeGuard.register crashed` → SO 加载失败兜底（x86_64 模拟器上属预期）
  - `submitReceipt invalid appId or context`（status=-200）→ 配置错误，找开发

**3. 管理员页入口**：设置 → 管理员（需管理员权限账号）→ 「复制设备指纹」。

## 六、已知限制与风险提示

1. **x86/x86_64 模拟器不包含 SO**（APK abiFilters 只打 arm64-v8a + armeabi-v7a）：Intel 模拟器上 GeeGuard 必定初始化失败并走兜底，属预期行为，不算 bug（TC-F3 验证的正是兜底不 crash）。功能主流程测试请用 arm64 模拟器或真机。
2. **隐私协议 gate 当前默认同意**（方案 A，无 UI 开关），"未同意不采集"路径暂无用户可达入口，本轮可不测；若后续合规收紧再补用例。
3. **拦截策略对模拟器/root 设备的表现取决于后端配置**，测试侧的职责是记录实际表现并与产品/后端对齐，不预设拦或不拦。
4. token 不做本地持久化，每次冷启动重新采集，属设计预期。
5. 老版本（图灵盾时期）可能仍向所有接口发送 `rceDeviceToken` header，后端应忽略；TC-G1 覆盖。
