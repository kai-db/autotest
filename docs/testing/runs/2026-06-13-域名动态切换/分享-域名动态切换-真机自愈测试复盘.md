## 0. 这次分享想讲清楚的事

和上一篇 HTTPDNS（逼出 Critical 缺陷）不同，这次没有惊天 BUG，但有三件更日常、更可复用的事：

1. **没有方案文档时，用例怎么从一个 diff 机械映射出来**；
2. **真机黑盒撞到"测不到"的路径时，怎么诚实处理**——不是糊一个 PASS，也不是误判 FAIL，而是**用证据证明"为什么测不到"**，再说清楚替代验证在哪；
3. **测试不只是判 PASS/FAIL，推理本身能逼出设计问题**——OBS-01 就是"读着代码 + 对着真机日志"想出来的，顺手给了最小修复。

## 2. 第一步：从一个 diff 生成用例

**核心方法：diff 改了什么行为 = 用例落点；自己提炼的不变量 = 验证标准。**

### 2.1 从代码提炼不变量（这是判据来源）

读完链路，提炼出 5 条不变量，每条都能变成用例：

1. `domainList` 永不为空（兜底注入保证 selectBestDomain 有候选）
2. 健康探测在后台线程、不阻塞启动、单域名探测 ≤2.5s
3. 探测/切换期间 currentDomain 被改写 → 放弃本次回退（防互相覆盖）
4. `onRequestSuccess` 仅对当前域名生效
5. `resetUrl()` 始终锁外调用（防死锁）

### 2.2 按执行成本分层

| 层 | 测什么 | 成本 | 能不能测 |

| **A JVM 单测** | OSS 解析 / 拦截器故障分类 / URL 解析的纯逻辑契约 | 低（无设备） | ✅ 跑现成 16 例 |
| **B 真机 logcat** | 启动健康探测 / 兜底 / 自愈端到端 | 中（需设备） | ✅ 取证 |
| ~~请求级单域名切换~~ | 阈值/冷却/切换决策 | — | ❌ **非 root 测不到（见 §5）** |

## 4. 第三步：真机测试手法

### 4.1 可逆断网（不破坏登录态/环境）

```bash
adb -s <设备> shell svc wifi disable && adb -s <设备> shell svc data disable   # 断网
adb -s <设备> shell svc wifi enable  && adb -s <设备> shell svc data enable    # 恢复（测完必做）
```

> 为什么不用清数据/切环境：会丢登录态 + 切回正式环境（危险操作红线）。`svc wifi/data` 是可逆、不碰 App 的最干净手法。

### 4.2 logcat 锚点抓取（看行为，不看猜测）

关键锚点：
- `checkCurrentDomainHealth: 当前域名 X 可达，无需处理` — 健康探测可达分支
- `isReachable: X 不可达 - UnknownHostException` — TCP 探测失败
- `不可达且无可达备选，清除固化的当前域名并回退主域名` — 全不可达回退分支

- `onConnectivityFailure` / `域名切换 A -> B` — 请求级切换（本次未触达，见 §5）

### 4.3 危险操作红线（全程遵守）
不登出、不清数据、不切环境、不碰转账/签名。钱包 App 误操作不可逆。

## 5. ⭐ 第四步：撞到测试边界，怎么诚实处理

这是本次最有分享价值的一段。

**预期**：运行中断网 → 下拉刷新触发请求 → 拦截器抓连通性异常 → `onConnectivityFailure` → 累积到阈值切域名。
**实际**：刷了半天，`onConnectivityFailure` **0 次触发**。

不糊 PASS，也不判 FAIL，而是**去查为什么**：

**证据 1——业务请求被 App 层守卫提前短路了**：
```
E [FLogger:http_request]: http request fail,url=dao/v1/batch_user_info,code=-100,message=网络未连接
RequestCore.call (DeBoxHttpRequest.kt:321)   错误码：-100，错误信息：网络未连接
```
设备整体断网时，`DeBoxHttpRequest` 直接以 `-100 网络未连接` 返回，**根本不进 OkHttp/DomainSwitchInterceptor**。

**证据 2——系统代理这条路也被堵死**：
```kotlin
// RetrofitFactory.getOkHttpClient()
.proxy(Proxy.NO_PROXY)   // OkHttp 绕过系统代理 → settings put global http_proxy 无效
```

**结论（诚实标注，非缺陷）**：
> 非 root 真机**无法黑盒触发"请求级单域名故障切换"**——设备级断网被 -100 守卫挡在 OkHttp 之前；系统代理被 NO_PROXY 绕过；选择性只封 debox.pro 保留 dbxsocial.com 需 root 改 hosts / 网络层注入。该特性的设计场景是「**设备有网、但单域名被 DNS 污染/IP 封堵**」，此时设备连通性检查通过、请求进 OkHttp 抛异常、切换才触发——这条契约**已由 A 层 UT-05~12 直接覆盖**（各异常类型→正确上报 host/path；第三方 host 不污染；read-timeout 不计入）。

→ TC-T-001 标 **⏸️ 跳过**，并写明替代验证在哪。**"测不到"也是结论，前提是你能证明为什么测不到。**

## 6. 第五步：测出来的亮点——自愈闭环端到端打通

虽然请求级切换测不到，但**启动健康探测的自愈链路**真机完整跑通了，而且证据自成闭环：

**断网冷启动（TC-T-002）** — 健康探测全不可达回退：
```
21:16:54.246  isReachable: debox.pro 不可达 - UnknownHostException     ← TCP 探测（后台线程 tid 21942）
21:16:54.249  isReachable: dbxsocial.com 不可达 - UnknownHostException  ← 2 域名共 3ms，DNS 即时失败，不卡启动
21:16:54.249  checkCurrentDomainHealth: debox.pro 不可达且无可达备选，清除固化的当前域名并回退主域名
```

**恢复网络重启（TC-T-003）** — 证明上一步真的清了固化域名、且能自愈：
```
restoreFromCache: 缓存域名无效(), 回退到 debox.pro   ← domain_current 已被 T-002 清空（SP 持久化生效）
checkCurrentDomainHealth: 当前域名 debox.pro 可达，无需处理
→ 46 个 code:1 成功响应，完全恢复
```

> 两条用例**串成一条证据链**：T-002 清固化域名 → 持久化到 SP → T-003 读到空值回退 → 探测可达 → 正常。比单看一条日志有说服力得多。

**本轮汇总：A 16 PASS + B 9 PASS / 1 跳过 / 0 FAIL（共 26 条，25 PASS）。**

## 7. 第六步：测着测着，逼出一个设计问题（OBS-01）

判完 PASS 不是终点。盯着 TC-T-002 那条"全不可达→回退 HOST"，顺着推了一步：

**这个 else 分支什么时候才触发？** —— 只有 currentDomain 和**所有备选（含 HOST/兜底）都不可达**时。换句话说，**只有 HOST 自己也连不上时才会走到这里**（否则会走上面的 healthy 分支切到 HOST）。

**那"回退 HOST"在它真正触发的场景里，是不是无效操作？** —— 是。HOST 都连不上了，回退 HOST 没有任何收益。

**但它有没有副作用？** —— 有。它会 `remove(domain_current)`。设想：某用户因 debox.pro 被针对性封堵，已故障切换到 `dbxsocial.com`；进地铁断网重启 App → 健康探测发现全不可达 → **误清掉已生效的 dbxsocial.com，退回仍被封的 debox.pro** → 出地铁后要重新累积 3 次失败、过冷却才能切回。

→ **结论：这个分支"在它能触发的所有场景里收益为零，却带来一个真实的体验回退"**。记为 OBS-01（非阻断，置信度~75%）。

### 最小修复（只改 else 分支 + 同步 KDoc）

```kotlin
} else {
    // 全部备选（含 HOST/内置兜底）也不可达：强烈暗示设备整体离线，而非当前域名被针对性封堵
    // ——只要 HOST 或任一备选可达就会走上面的 healthy 分支，到不了这里。
    // 回退 HOST 无收益（HOST 同样连不上），却会清掉用户已生效的故障切换选择。保留不动，
    // 交由网络恢复后的请求级故障切换接管。
    LogUtils.w(TAG, "...不可达且无可达备选（疑似设备离线），保留当前域名，待网络恢复后由请求级切换接管")
}
```
- **零能力损失**：删掉的回退在所有触发场景里都是无效操作。
- **修掉副作用**：`changed` 保持 false → 不写 SP、不 resetUrl、currentDomain 原样保留。
- **自愈不变**：网络恢复后由请求级 `onConnectivityFailure` 继续接管。
- 验证：`compileDebugKotlin + DomainManagerTest` → **BUILD SUCCESSFUL** 回归绿。

> 这条修复**不是测出来的崩溃，是推出来的设计味道**。测试的价值不止于判 PASS/FAIL，读懂代码后多想一步，常能发现"能跑但不该这么写"的地方。

## 8. 关键收获（可复用的方法论）

1. **没有方案文档时，先提炼不变量**：从 diff + 注释读出"应该满足什么"，不变量就是用例判据。
2. **写用例时就标清楚"哪层测不到"**：A 层覆盖不到实例逻辑（无 Robolectric），要在用例里写明下沉 B 层，而不是假装覆盖。
3. **"测不到"也是合格结论，但必须用证据证明**：-100 守卫日志 + NO_PROXY 源码，证明为什么非 root 真机触不到请求级切换，再指明替代验证。
4. **可逆、不碰生产数据**：`svc wifi/data` 断网、测完必恢复、清代理残留。
5. **让证据串成链**：T-002 清域名 → T-003 读到空值恢复，两条串起来比单条日志强。
6. **判完 PASS 多想一步**：盯着一个分支问"它什么时候触发、那时它有用吗、有没有副作用"，逼出了 OBS-01。
7. **修复要最小且论证充分**：只改 1 个分支，先讲清"为什么删掉零损失"，再动手。
