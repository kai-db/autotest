# AutoTest 项目技术分享

> Android 真机自动化测试框架 · v1.8.1
> 一句话定位：**AI 在环探索发现问题 → 固化为确定性用例 → CI 自动回归** 的闭环测试体系
> 适用：技术分享会 / 新人 onboarding / 对外介绍
> 配套深读：架构 `01` · 技术方案 `02` · 开源借鉴 `08` · AI 机制 `09` · 测试规范 `testing/TEST_GUIDE.md`

---

## 0. 30 秒讲清楚这是什么

传统 UI 自动化的两难：**纯脚本**（Espresso/Appium）写得累、UI 一改就挂；**纯 AI 测试**（Midscene/Maestro AI）灵活但慢、不确定、没法进 CI。

AutoTest 的答案是把两者**焊接**起来：

```
   AI 在环（探索/首跑/修复）              确定性执行（CI 回归）
┌────────────────────────────┐      ┌────────────────────────────┐
│ Claude Code + mobile-mcp    │ 产出 │ autotest AAR(Espresso/UiAuto)│
│ 看屏幕·规划·判定·读知识库   │─────►│ 零 LLM 依赖·缓存回放·自愈兜底 │
│ 产出：用例缓存 + 知识库     │◄─────│ 报告回流：自愈/AI断言/根因    │
└────────────────────────────┘ 回流 └────────────────────────────┘
```

**核心理念一句话：Agentic authoring + Deterministic execution（AI 在环编写、确定性回放执行）。**
所有 LLM 能力（AI 定位兜底、AI 断言）都只定义接口、外部注入——探索期注入实现去探索，CI 期不注入、框架自动降级为确定性行为并留痕。这是它区别于纯 AI 测试工具的根本取舍。

**一组数字**：70 个源码文件 / 19 个模块 / 约 5790 行 main / 311 条单测 / AAR 发布到 mavenLocal 供项目依赖。

## 2. 借鉴了哪些开源项目（每个借鉴点都有源码注释实证）

AutoTest **不是 fork 任何单一项目**，而是在 Android 官方测试栈之上，吸收了 6 个开源项目各一块"AI 时代的能力拼图"。**Kaspresso 提供架构骨架，其余各补一块 AI 能力。**

| 开源项目 | 借鉴的具体功能 | 在本项目的落点 | 关键收获 |
|---|---|---|---|
| **Kaspresso** | 双链拦截器（Behavior+Watcher）、step DSL、BaseScenario、Device API、TestCase 四段式、flakySafely、logcat/弹窗处理 | `intercept/` `dsl/` `device/` `base/` `stability/FlakySafely` | **架构骨架**——观察与恢复严格分离、只有 behavior 能影响结果 |
| **Healenium** | 元素指纹自愈 + "**静默自愈会掩盖真实 UI 回归**"的教训 | `selector/HealingEngine` `FingerprintStore` | 自愈必须**留痕可审**，不是黑盒银弹 |
| **midscene.js** | AI 跑一次 → 缓存 → 确定性回放；cache 三态读写 | `bridge/`（CachedCase + CacheMode） | 把"AI 探索"沉淀成"零 LLM 回放" |
| **Marathon** | "flakiness 是统计问题，用历史数据而非固定次数解决" | `stability/AdaptiveRetryPolicy` `TestHistoryStore` | 重试预算由历史通过率反解，不拍脑袋 |
| **Maestro** | `assertWithAI` 的 optional 设计——AI 断言默认软失败、留痕不挂测试 | `assertion/AiAsserter` | AI 断言是兜底而非主路径，防 LLM 抖动打爆 CI |
| **AppAgent / Mobile-Agent** | 知识沉淀（页面元素资产）+ **危险操作 pre-action 比对**（GUI-Critic） | `docs/testing/app-knowledge/` + `dangerous-ops.md` | 钱包 App 点击前比对危险清单，误操作不可逆 |

底层还直接用了：**Espresso IdlingResource**（同步机制）、**UiAutomator**（跨进程定位）、**OkHttp Interceptor 链**（`runWithRecovery` 的 proceed/重试结构）。

> 分享话术：「Kaspresso 给了我们一副**骨架**，Healenium / midscene / Marathon / Maestro 各给了一块**器官**——分别是自愈、回放、统计重试、AI 断言。我们做的是把这些在'AI 在环'这个新场景下重新组装。」

## 3. 九大技术模块深挖（分享会主体）

### 3.1 selector —— 三级降级定位 + 指纹自愈

**问题**：UI 文案/布局微调后选择器失效，是 UI 自动化最大维护成本。

**设计**：
- `SelectorSpec` 是 sealed class AST（`Leaf`/`Not`/`And`/`Or`），两种消费：`toDnf()` 展开析取范式驱动 UiAutomator `BySelector`（原生 By 不支持 Not，靠 DNF 展开 + Not 后置过滤）；`matches(snapshot)` 纯谓词匹配。
- `SelfHealingLocator` 三级降级链：
  1. **L1 确定性定位**：按 DNF 备选逐个查，命中即回写指纹
  2. **L2 指纹自愈**（零成本，纯本地）：dump 层级 XML → 候选集 → 与历史指纹算**加权相似度**
  3. **L3 AI 兜底**（可选注入）：把 selectorKey + hierarchyXml 交给 LLM
- `HealingEngine.score()` 亮点算法：res-id **0.40** / text **0.30** / desc **0.20** / class **0.10** 加权，空属性不计分并**重新归一化**；字符串相似度三档（相等 1.0 / 包含 0.8 / 归一化 Levenshtein 再打 6 折）；阈值 **0.75** 以下宁可降级不硬认。

**亮点**：自愈带置信度可解释、生成 `LocatorEvent` 进报告要求人审——把"自愈"从"掩盖回归的银弹"变成"带留痕的降级保护"（Healenium 的教训）。**确定性命中刻意不记**避免噪音。

### 3.2 bridge —— 固化桥（缓存回放）

**问题**：AI 黑盒探索每次都调 LLM，慢且不确定。把 AI 第一次跑通的路径固化成可回放缓存。

**设计**：
- `CachedStep.target` 存的是**完整 ElementSnapshot 快照**而非裸选择器——回放时 `toSelectorSpec()` 按 res-id→desc→text 稳定性排序构建选择器，再走三级自愈，所以**缓存里的元素微调后仍可命中**。
- `CacheMode` 三态：**READ_WRITE**（探索）/ **READ_ONLY**（CI，拒写留痕保证确定性）/ **WRITE_ONLY**（强制重探索）。
- `CacheReplay.toScenario()` 把缓存转成框架 Scenario——**回放用例与手写用例走同一条产出链路**（同样的拦截器、证据、报告）。
- 防注入：拼 shell 前 `requireSafePackage()` 正则校验。

**亮点**：三层固化阶梯——**AI 黑盒探索 → JSON 缓存确定性回放 → Kotlin 白盒用例**，成本递减、稳定性递增。存快照而非选择器让"录制回放"这种传统脆弱方案抗 UI 漂移。

### 3.3 stability —— 统计化稳定性

**问题**：UI 测试天生 flaky，但"无脑固定重试 N 次"既浪费稳定用例、又给真 bug 假性通过的机会。

**设计**：
- `FlakyClassifier`（规则链）：自定义规则 → 内置关键词（timeout/stale object…）→ 内置正则 → **HARD_FAIL 保守兜底**。取向："宁可漏判 FLAKY 多跑一次，不可把真 bug 误判成 FLAKY"。
- `AdaptiveRetryPolicy` 数学亮点：按历史通过率 p 反解达到目标成功率 T 的尝试次数 **n = ⌈ln(1−T)/ln(1−p)⌉**（来自 1−(1−p)ⁿ ≥ T）。p=1→0 次、p=0→封顶 maxRetries。
- `TestHistoryStore`：caseId → 最近 50 次 pass/fail 滚动窗口，JSON 跨 run 积累，是预算的数据底座。
- `flakySafely()`（代码块级重试）：**只重试 UI 时序类异常**（AssertionError/IllegalStateException），**刻意排除 NPE/RuntimeException**（"几乎总是真 bug，重试只会拖到超时掩盖根因"）。

**亮点**：重试次数从拍脑袋常量变成历史通过率推导的概率预算——稳定用例 0 重试不浪费、flaky 用例足额。可重试异常白名单防止重试沦为"掩盖 bug 的拖延器"。

### 3.4 intercept —— 双链拦截器（最能讲的架构点）

**问题**：在不污染测试主逻辑前提下，统一插入日志/截图/性能/内存采集，以及失败时自动恢复。

**设计——严格分离的双链**：
- **watcher 链**（6 钩子 before/after/onFailure × Action/Step）：**纯旁路观察，永不影响结果**，每个调用包在 `safely{}` 里——拦截器自身异常被吞但**留痕**。
- **behavior 链**（`tryRecover()`）：**唯一允许影响结果的链**。失败 → 按序让 behavior 尝试恢复 → 任一成功就**重试一次** → 全链无解抛错。
- 6 个内置拦截器：Logging / Screenshot（**默认仅失败截图**，scale 0.5+quality 80 省 ~75% 存储）/ Logcat（失败 dump 300 行）/ Performance（P50/P95 百分位）/ Memory（PSS 相对基线增长检泄漏）/ **DialogDismiss**（纯 behavior 失败恢复——watcher 链保持纯旁路契约，默认词表不含「确认」类按钮防误点危险确认）。

**踩坑沉淀**：DialogDismiss 改成"**一次抓取所有 clickable 本地匹配**，替代每步 23 次跨进程 findObject"——被测 App 永不 idle 时这是主要耗时来源。

**亮点**：双链分离是教科书级关注点分离。可现场对比"如果观察和恢复混在一起会怎样"。

### 3.5 engine —— 监工模式（铁律即代码）

**设计**：
- `TestRunner`：单用例生命周期编排（envReset→before→run→after→报告），不依赖 JUnit Runner。
- `TestSuite`：**只暴露 `runAll()` 不暴露 `runFailed()`**——把"回归必须全量跑"的铁律写进 API 形状。
- `MonitorMode`：6-Phase 状态机（环境→全量→写文档→修复→回归→验收），亮点是 `runAllWithTimeout()`——**独立线程跑 + 硬超时**，App 卡死时超时记一条合成 FAIL 让监工闭环进入修复而非永久挂起（AI 驱动场景刚需）。

**亮点**："约束即代码"——组织铁律固化进 API 形状和引擎逻辑，而非靠文档约束。

### 3.6 dsl —— 步骤式 DSL

`scenario{}` 提供：`step` / `stepIf`（条件）/ `flakyStep`（步内重试）/ `stepWithRecovery` / `repeat` / **`forEach`（数据驱动：数据集×操作展开为多个独立步骤，失败直接看出挂在哪条数据上）**。每个 step 自动成为证据/计时/恢复的最小单元。`BaseScenario` 把登录等常见流程封装为可复用类，`include()` 一行嵌入。

### 3.7 diagnosis —— 失败根因签名

`LogcatAnalyzer` 正则识别 4 类根因：OOM / CRASH（FATAL EXCEPTION）/ ANR（按包名过滤）/ NATIVE_CRASH（Fatal signal）。**OOM 优先于普通 crash**。产出 `RootCause(type, signature, evidenceLine)`，signature 用于聚类同类失败。报告里直接呈现"环境问题 vs 产品 bug vs 用例问题"判定依据。

### 3.8 assertion —— AI 软断言

`AiAsserter.assertWithAi(desc, optional=true)` 三态：无评估器→SKIPPED 留痕；optional=true（默认软）→ FAIL 只告警不挂测试；optional=false（硬）→ 抛 AssertionError。**只用于确定性断言写不出来的场景**（视觉状态/canvas/RN 动态文案）。结果进报告独立通道。

### 3.9 report —— 非确定性行为的审计台账

`ReportCollector`（TestWatcher）汇聚：失败时自动 FlakyClassifier 分类 + LogcatAnalyzer 根因 + 回填截图。`RunReport` 含 5 独立 section：steps / failures / **aiAssertions** / **healingEvents（自愈事件需人审）** / summary。`HtmlReporter` 生成自包含 HTML，AI 断言段/自愈段都带语义说明。**自愈/AI 断言/根因都有独立可解释 section，而非淹没在 PASS/FAIL 里。**

## 4. AI 是怎么驱动测试的

### 4.1 两条路线 + 闭环

```
路线 A（AI 黑盒探索）：自然语言 → Claude Code 规划 → mobile-mcp 操控真机 → 截图理解 → 判定
路线 B（CI 确定性回归）：git push → Gradle connectedAndroidTest → autotest 执行 → JSON/HTML 报告
闭环：AI 发现 bug → 固化为 autotest 用例/缓存 → 加入 CI → 每次发版自动回归
```

### 4.2 为什么不在 App 里内置 AI

| 方案 | 缺点 |
|---|---|
| 框架内调 AI API（已废弃） | 需 App 端发 HTTP、AI 看不到屏幕、无法灵活交互 |
| **Claude Code + mobile-mcp（采用）** | AI 能看截图、灵活对话、**无需改 App 代码** |

mobile-mcp 提供 list_devices / launch / screenshot / list_elements / click / type / swipe / press 等工具，AI 通过它"看屏幕→规划→操作→再看截图判断"。

### 4.3 六大机制如何焊接 AI 与确定性

| 机制 | AI 在环时 | CI 执行时 |
|---|---|---|
| 三级自愈定位 | 注入 AiLocatorFallback 兜底 | 不注入，降级到 L2 指纹自愈 |
| 固化桥缓存 | READ_WRITE 产出缓存 | READ_ONLY 确定性回放 |
| AI 软断言 | 注入评估器评估视觉状态 | 不注入，记 SKIPPED 留痕 |
| 统计重试 | — | 历史通过率驱动预算 |
| 双链拦截器 | 全程证据采集 | 同左 |
| 根因签名 | AI 读结构化根因修复 | 报告自动回填 |

**关键原则：LLM 只在 authoring 阶段在环；execution 阶段 AI 接口不注入，框架自动降级为确定性行为并留痕。**

### 4.4 AI 测试 session 标准开场

1. 读 `app-knowledge/`（页面元素 + 已知弹窗 + **dangerous-ops.md**）
2. 读 `TEST_GUIDE.md` 铁律（危险操作 pre-action 比对）
3. preflight：设备在线 / App 已装 / 测试环境 + 已登录
4. 有缓存的用例优先回放，只对新用例做探索
5. 探索产物**三回写**：知识库（人读）、用例缓存（机器回放）、TEST_CASES.md（规格）

## 5. 测试规范（怎么测才靠谱）

### 5.1 七条铁律

1. **AI 驱动** — 全程自主执行，不等人指示每一步
2. **按用例执行** — TEST_CASES.md 是唯一用例来源
3. **监工模式** — `/loop 5m` 定时检查，防 AI 卡住
4. **最小人工介入** — 除验证码等必须环节外全自主
5. **修复必须合规** — 证据驱动 / 不引入新 bug / UI 正常 / 最小改动
6. **先读知识库** — session 先读 app-knowledge/，探索产物回写
7. **危险操作 pre-action 比对** — 点击前比对 dangerous-ops.md，钱包 App 误操作不可逆，禁止清数据/登出/切环境

### 5.2 监工 6-Phase 闭环

```
Phase 1 确认环境 → Phase 2 全量测试(P0→P1→P2) → Phase 3 先写文档
→ Phase 4 修复(根因→改码→记录) → Phase 5 全量回归
   ├ 仍有 FAIL → 回 Phase 3
   └ 全 PASS → Phase 6 全量验收(不改码跑一遍) → 结束
```
关键：每轮**全量**跑（防回归）、**先记录再修复**、验收是独立全新测试。

### 5.3 危险操作红线（钱包 App 专项，借鉴 Mobile-Agent GUI-Critic）

点击前若命中 dangerous-ops.md（转账/删钱包/登出/清数据/切环境/授权签名）→ **停下、截图、比对用例**；用例未明确要求一律规避。**宁可 FAIL 不误点。**

### 5.4 产物规范（每次测试一个目录）

```
docs/testing/runs/YYYY-MM-DD-功能/
├── cases.md      # 分层用例（A静态/B单测/C集成/D真机 + P0/P1/P2）
└── results.md    # 每轮结果 + Bug 记录（根因/修复/验证）
app-knowledge/    # 页面元素表 + 弹窗 + 危险操作（探索沉淀，跨轮复用）
cache/            # CachedCase JSON（AI 产出、回归回放）
```

## 6. 一个真实案例：HTTPDNS 测试逼出 Critical 缺陷

> 完整复盘见 `runs/2026-06-12-阿里云HTTPDNS/分享-AI驱动测试全流程复盘.md`

**输入**：debox `feat/ali-dns` 分支改动 + 方案文档 → 机械映射出 67 条分层用例（A 静态 / B 单测 / C 集成 / D 真机）。

**推进**：框架前置 → A 层静态核对（接入点是否真落地）→ B 层 JVM 单测（**审查发现覆盖缺口，补 13 个单测**）→ D 层真机。

**真机手法**：dex 字符串验真（防测错包）、private_dns 模拟 DNS 异常（可逆、不碰 App 数据）、本地 HTTP 服务 + adb reverse 模拟 OSS、logcat 锚点抓行为。

**核心发现（Critical）**：拿**真实线上 OSS 配置**去核对，发现线上用**扁平格式** `httpdns_enabled`，实现只读**嵌套段** `httpdns.enabled` → 配置被当"段缺失"忽略、**HTTPDNS 静默失效**，线上只有一条 debug 日志无报错。

**为什么单测/功能测都漏**：单测用规范格式、本地模拟恰好用对格式——**是"拿真实线上配置核对"这一步逼出来的**。

**闭环**：报告 + 给修复选项（改 OSS / 改代码）→ 用户决策 → 改 `parseSection` 兼容扁平格式 + 3 单测 → 端到端真机回归（测试环境坏 DNS 下 19 个请求 200）→ 修订方案文档消除歧义 → 现场全部复原。

**正式环境延伸（两类缺陷的递进）**：切到正式环境（生产 OSS `conf_v2.json`）回归，BUG-001 修复在生产生效（扁平配置正确识别）；同时逼出第二类缺陷 **FOUND-01——生产域名 `debox.pro` 未加 EMAS 控制台**（坏 DNS 下空结果降级、兜底形同虚设）。运维加域名后复测，**生产坏 DNS 下 8 个 `debox.pro` 请求 200 成功**，兜底闭环打通。

> 关键洞察：测试环境逼出**代码缺陷**（配置格式契约），正式环境逼出**外部配置缺陷**（控制台漏配）。两者都隐蔽——前者只一条 debug 日志、后者只埋点偏高，**都是"拿真实环境配置去核对"才暴露的**。

**这个案例的分享价值**：展示了 AI 驱动测试不是"点点点跑用例"，而是**从代码+文档生成用例、分层逼近、跨环境（测试→正式）拿真实配置核对、发现问题给选项、修复闭环**的完整工程方法。

## 7. 一以贯之的工程哲学：留痕不静默

这是全框架最能引发共鸣的价值观，每个模块都贯彻：

| 场景 | 不静默的做法 |
|---|---|
| 自愈命中 | 生成 LocatorEvent 进报告，要求人审（可能是真 UI 回归） |
| AI 断言无评估器 | 记 SKIPPED 进报告，不假装通过 |
| 拦截器自身异常 | `safely{}` 吞掉但 log 留痕 |
| 缓存 READ_ONLY 拒写 | 留痕，不静默丢弃 |
| 根因分析失败 | 降级为无根因，不影响失败记录本身 |
| flaky 误判风险 | 保守兜底 HARD_FAIL，宁可多跑不可漏判 bug |

> 一句话：**没有任何静默兜底**。所有非确定性行为、所有降级、所有异常，都 log / 进报告。

### 9.2 Q&A 可能被问到的

| 问题 | 回答要点 |
|---|---|
| 和直接用 Appium/Maestro 的区别 | 它们要么纯脚本要么纯 AI；我们是"AI 探索 + 确定性回放"双相，CI 期零 LLM |
| AI 会不会乱点坏数据 | dangerous-ops.md pre-action 比对 + 测试环境校验 + 禁清数据/登出/切环境 |
| 自愈会不会掩盖真 bug | 自愈命中必生成事件进报告要求人审（Healenium 的教训），确定性命中才静默 |
| flaky 重试会不会放过真 bug | 可重试异常白名单（排除 NPE）+ FlakyClassifier 保守兜底 HARD_FAIL |
| 缓存的用例 UI 改了会挂吗 | 缓存存元素快照而非选择器，回放走三级自愈，抗微调 |
| 为什么不在 App 内置 AI | AI 看不到屏幕、要改 App 代码、无法灵活交互（§4.2） |
